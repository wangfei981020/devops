# 版本号规范

一句话：**语义化版本（SemVer），`v` 前缀，预发布只允许 `alpha` / `beta` / `rc` 三档。**

```
v<主版本>.<次版本>.<修订号>[-<预发布>.<序号>]

v0.1.0          开发期
v1.0.0          第一个正式版
v1.2.0-rc.1     发布候选
```

`tooling/scripts/build-image.sh` 会按这个规则校验，不合规直接拒绝构建。

---

## 各段什么时候加

| 段 | 什么时候 +1 | 例子 |
|---|---|---|
| **主版本** MAJOR | 破坏性变更：接口删字段 / 改语义、数据结构不兼容、升级需要人工干预 | v1.4.2 → **v2**.0.0 |
| **次版本** MINOR | 新功能，向后兼容 | v1.4.2 → v1.**5**.0 |
| **修订号** PATCH | 只修 bug，不加功能 | v1.4.2 → v1.4.**3** |

升了高位，低位归零。`v1.4.9` 的下一个功能版是 `v1.5.0`，不是 `v1.4.10`。

## v0.x 与 v1.0.0 的分界

**`v0.x.y` 阶段不承诺任何兼容性。** 数据结构、接口、配置项都可能改，升级可能需要人工处理。这是刻意的——功能还在成形，过早锁定兼容性会让每个改动都背上包袱。

**发 `v1.0.0` 意味着一件事：从此对外承诺兼容性。** 达到下面全部条件才发：

- 一期功能闭环，客户能独立完成日常工作
- 数据库结构稳定，不再有破坏性迁移
- 对外接口定型（含 MCP 工具签名）
- License 机制（激活 / 降级 / 宽限）跑通并验证过
- 有安装文档、升级文档、回滚步骤

**当前处于 `v0.1.0`** —— 前端重写完成、后端已归位、一条链路（主机列表）跑通。

## 预发布三档

| 后缀 | 给谁 | 稳定性 |
|---|---|---|
| `-alpha.N` | 只在内部环境 | 可能跑不起来 |
| `-beta.N` | 少量客户试用 | 功能齐了，可能有 bug |
| `-rc.N` | 发布候选 | 认为可发；无阻塞问题就原样发正式版 |

排序：`v1.0.0-alpha.1` < `-beta.1` < `-rc.1` < `v1.0.0`（正式版最大，这是 SemVer 规定的）。

**预发布版本禁止推对外仓库**，构建脚本会拦。理由很实际：一旦 `-rc.1` 进了对外仓库，就没法阻止别人拿它当正式版部署到生产，出了问题却按正式版的标准来问责。

## 三个版本号的关系

一次发布涉及三个地方，别混：

| 位置 | 填什么 | 什么时候变 |
|---|---|---|
| 镜像 tag | 产品版本，如 `v0.1.0` | 每次发布 |
| `Chart.yaml` 的 `appVersion` | 同上（不带 `v`，如 `0.1.0`） | 每次发布 |
| `Chart.yaml` 的 `version` | **chart 自身**的版本 | 只有模板结构变了才升 |

`version` 独立演进是有意的：只改了镜像 tag 重新部署，chart 本身没变，不该跟着升版——否则 chart 仓库里会堆一堆内容完全相同的版本。

**前后端共用一个产品版本号。** 它们在同一个 chart 里、一起发布、一起回滚，分开编号只会带来"前端 v0.3.1 配后端 v0.2.7 行不行"这种没人答得上来的问题。

## 怎么发一个版本

```bash
# 1. 构建（版本号会被注入产物，前端「关于」页和 /version.json 都能查到）
tooling/scripts/build-image.sh ops-cmdb v0.1.0

# 2. 推本地 Harbor 验证
tooling/scripts/build-image.sh ops-cmdb v0.1.0 --push

# 3. 部署
helm upgrade --install cmdb ops-cmdb/deploy/helm -n ops-cmdb \
  -f ops-cmdb/deploy/helm/values-local.yaml \
  --set frontend.image.tag=v0.1.0

# 4. 核对每个副本实际跑的版本
kubectl -n ops-cmdb get pod -l app.kubernetes.io/component=frontend -o name \
  | xargs -I{} kubectl -n ops-cmdb exec {} -- wget -qO- 127.0.0.1:8080/version.json
```

## 两条硬约定

1. **不用 `latest` 标签。** 部署里写 `latest`，出问题时没人说得清当时跑的是哪份代码，回滚也没有目标。
2. **版本号只能由构建脚本注入。** 不要手工 `docker build`——漏传 `--build-arg VERSION` 会静默落成 `dev`，上一代四个前端全踩过，线上排障时完全看不出前端是哪一版。
