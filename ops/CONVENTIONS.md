# 工程约定

> 新系统进 `ops/` 之前先读这份。所有条目都来自实际踩过的坑，**每条都写了为什么**——
> 遇到文档没覆盖的新情况时，照着"为什么"去推导，而不是猜。
>
> 这里的约定优先级高于个人习惯。要改，先改这份文档。
>
> **授权 / License 相关的约定单独一份**：[LICENSING.md](LICENSING.md)。

**贯穿全文的一条总原则：**

> **出错时必须看起来像出错。**
>
> 这套系统里绝大多数事故不是"报错了"，而是"没报错但结果是假的"——
> 失败被渲染成空列表、漏翻的文案静默回退、白标换色后有一处没跟着变、
> 版本号落成 `dev`。它们的共同点是**不报错、看起来正常、只有用户先撞见**。
> 下面每一条约定，本质上都是在把某种"静默做错"变成"当场失败"。

## 1. 目录与依赖

```
ops/
├── packages/            前端共享包，被所有产品引用
│   ├── design/          设计 tokens、主题、白标
│   ├── i18n/            语言包与格式化
│   ├── ui/              基础组件、四态、DataTable
│   └── api/             OpenAPI 类型生成、请求客户端、错误归一
├── ops-kit/             后端共享 Go 包（licensekit 等）
├── ops-<产品>/          一个产品一个目录
│   ├── frontend/
│   ├── backend/
│   └── deploy/helm/
└── tooling/scripts/     构建与检查脚本，CI 与本地共用
```

**依赖方向单向**：`ops-*/frontend → packages/* → packages/design`。
不允许反向，不允许产品之间互相引用。

**共享的东西为什么不放进某个产品目录**：放在任一产品下，其他产品就得反向依赖它，依赖图立刻成环。共享包必须是叶子。

**新增产品的动作**：建 `ops-<产品>/{frontend,backend,deploy}`，`pnpm-workspace.yaml` 的 `ops-*/frontend` 通配会自动纳入，不用改配置。

## 2. 前端

### 2.1 异步状态：四态，一个都不能少

**所有异步渲染必须包 `<AsyncBoundary>`**，它强制你提供 pending / empty / error / ready 四个分支，漏一个是编译错误。

```tsx
<AsyncBoundary
  state={fromQuery(query, (d) => d.length === 0, toLoadError)}
  pending={<TableSkeleton columns={[22, 10, 12]} rows={8} />}
  empty={<EmptyState title="…" reason="…" action={{ label: '…', onClick }} />}
  errorTitle={t('hosts:error.title')}
  retryLabel={t('common:action.retry')}
  onRetry={() => query.refetch()}
>
  {(data) => <DataTable data={data} />}
</AsyncBoundary>
```

**为什么**：过去的写法是 `{loading ? <Spin/> : data.length ? <Table/> : <Empty/>}` —— 这行代码里 **error 分支根本不存在**。请求失败时 `data` 是空数组，于是失败被渲染成「暂无数据」，看的人以为真的没数据，基于错的前提做了决定。它不报错、不白屏、监控也看不见，能活很久。

配套的三条硬规则：

| 规则 | 为什么 |
|---|---|
| `EmptyState.reason` **必填** | 「暂无数据」不给用户任何可行动信息。好的空态回答三者之一：还没配数据源 / 筛选太窄 / 确实没有 |
| `EmptyState.action` 类型是 `Action \| null`，**必须显式给值** | 写成可选参数的话绝大多数人不会传。强制写 `null` 是逼作者想一遍"这里真的没有下一步吗" |
| `ErrorState.retryLabel` **必填且无默认值** | 早期给了个中文默认值，结果英文界面的错误态出现一个中文按钮。错误路径平时走不到，这种漏译能活到客户手里 |

**空态还要再分**：「筛选后为空」和「本来就没数据」是两种空态，原因和出路完全不同，必须分开写。

🔴 **空态只能替换数据区，不能替换操作区。**

工具条（搜索 / 筛选 / 写按钮 / 下钻入口）必须放在 `<AsyncBoundary>` **外面**，
只让表格区受空态控制：

```tsx
<>
  <Toolbar … />                        {/* 永远渲染 */}
  <AsyncBoundary state={state} empty={<EmptyState … />}>
    {(data) => <><DataTable … /><Pagination … /></>}
  </AsyncBoundary>
</>
```

**为什么**：写在 `children` 里的话，`total===0` 时整条工具条连同按钮一起不渲染。
而「没有数据」恰恰是最需要点那些按钮的时刻 —— 同步按钮点不到就没法同步出数据，
形成死循环；全新部署的实例因此**根本无法完成首次接入**。
筛选筛空时也一样：用户会以为功能没做或自己没权限。

⚠️ 排查时别往权限上想：`WriteButton` 无权限只置灰并把原因挂 `title`，**从不隐藏**。
按钮彻底消失一定是空态分支。

⚠️ 空态下取不到 `data` 时，按钮该置灰就置灰，但**必须给出原因**
（`blockedReason`），不要因为拿不到数据就把按钮藏了 —— 那等于换个方式犯同一个错。

这条踩过不止一次（OPSCMDB-001，以及修它的过程中在「服务与入口」页又踩了一次），
所以写进约定而不是只留在问题档里。

**后端返回错误一律走 `httpx.Fail` / `FailKey`，不要裸写 `gin.H{"error": ...}`**：
裸的那种前端归一不出来，`detail` 会退化成一句
`DELETE /api/environments/1 → 409` —— 而原来那句话里真正有用的是
"还有 18 条资产在用"这个数字。实测踩过：后端把话说清楚了，前端却只显示了请求行。
带参数的动态消息用 `FailKey` + params，前端翻译（§2.6）。

**取错误信息一律用 `toErrorInfo(err)`，不要直接调 `normalizeError`**：客户端抛出来的是
`ApiError`，规范化结果在它的 `.info` 里。直接丢给 `normalizeError` 会走到兜底分支 ——
于是每一个错误的文案都退化成「请求失败，原因未知」，且 `retryable` 变成 true，
**403 也会被重试三次**。而"未知"看起来像个合理的兜底，没人会怀疑它。

### 2.2 「没有值」有四种语义，不能都渲染成空白

用 `<NoValue kind={...}>`：

| kind | 含义 | 视觉 |
|---|---|---|
| `na` | 该字段对这类对象本就不适用（自建机没有云机型） | 灰色 `—` |
| `notIngested` | 数据源没配，拿不到（集群没接 Prometheus） | 灰色斜体「未接入」 |
| `stopped` | 因状态而不再产生值（已销毁，停止计费） | 灰色文字 |
| `unknown` | 采集过但没拿到，**原因不明** | **警告色**——这是故障信号，不是空值 |

**为什么**：把它们统一成空白或 0，是上一版最大的一类问题。「采集失败」和「本来就没有」长得一模一样，看的人按后者理解，然后基于错的前提做决定。

`unknown` 用警告色是刻意的：它代表采集链路出了问题，值得被看见；和其他三种一样淡的话，故障就淹没在正常的空值里了。

**同理，成本列不能显示 `$0`**：$0 会被汇总统计当成"免费机器"，而真相是它不存在了。

**关联关系也适用这条**：一个"没有子项"的列表（这台机器上的 Pod、这个域名下的记录）至少要分三态，
由后端出一个显式的关系字段，而不是让前端拿 `list.length === 0` 去猜：

| 值 | 含义 | 界面 |
|---|---|---|
| `linked` | 关联上了，空数组 = 确认真的没有 | 正常空态 |
| `not_ingested` | 该关联的数据源没接进来 | `notIngested`，并说明去接什么 |
| `none` | 这类对象本就没有这种关系（独立数据库机不是集群节点） | `na` |

后两者都会渲染成"没有 Pod"，但一个要人去接集群，一个什么都不用做。压成布尔量就等于替客户
宣称"这台机器闲着"。

**判"缺口"时要排除对象本身已消失的情况**：已销毁的主机查不到对应节点是正常的，
按 `not_ingested` 报会让每台退役过的机器长期挂一条假缺口 —— 假缺口攒多了，真缺口就没人看了。

### 2.3 颜色只走 token

组件里**只允许**写语义类名（`bg-primary` / `text-muted-foreground` / `border-border`）。

禁止：颜色字面量（`#6E6CEF` / `rgb()` / `oklch()`）、Tailwind 默认色板（`bg-blue-500`）、黑白字面类（`bg-white`）。`tooling/scripts/check-hardcoded-colors.mjs` 会在构建前拦下。

**为什么**：白标能不能成立只取决于一件事——颜色有没有绕过 token 层。只要有一处写死 `bg-indigo-500`，客户换品牌色后那一处就不会变，**而且大概率没人发现**，因为它看起来仍然"是个紫色按钮"。

允许 `var(--ops-*)`：它没有绕过 token 层，白标照样生效。

### 2.3.1 产品级换肤只能覆盖 `--ops-*`，覆盖 `--color-*` 是死的

给某个产品做视觉差异化（换品牌色、换中性调、换圆角）时，
覆盖点**必须**是 `--ops-*` 和 `--radius-*`。

Tailwind 4 的 `@theme` 在**构建期把间接层拍平**。`@ops/design` 里写的

```css
@theme { --color-danger: var(--ops-danger) }
```

编译出的工具类不是 `var(--color-danger)`，而是

```css
.text-danger { color: var(--ops-danger) }
```

—— `--color-danger` 运行时**没有任何消费者**。

🔴 写错这一层的所有症状都指向"改生效了"：构建通过、无告警、
`getComputedStyle(root).getPropertyValue('--color-danger')` 返回新值，
**唯独界面不变**。实测查了很久（VIDEO-025）。

**判据（两条命令）**

```bash
grep -o '\.text-danger{[^}]*}' dist/assets/*.css   # 工具类真正引用谁
```
```js
getComputedStyle(元素).color                        // 元素实际拿到什么
```

两者不一致 = 覆盖层写错了。只查 `--color-x` 的值永远查不出来。

**改中性色改阶梯，不要逐个改语义色。**
`--ops-n0..n900` 12 档往下派生 background / surface / card / secondary /
muted / accent / border / input。逐个改语义色的话，漏掉一个就留下一块原色，
那种不一致看起来像随机的渲染问题。

⚠️ `--font-sans` 被整段内联成字面量字体栈，连 `var()` 都不剩。
换字体只能写显式 CSS 规则（`body, .font-sans, button, input { font-family: … }`），
改 token 无效。

**白标机制不受影响**：品牌入口是 `--ops-brand-h/c/l` 三个值，
accent 五档由它们在**运行时** `calc()` 推导。
（也正因为这一层是活的，写错时品牌色会唯独落地，进一步掩盖其余部分是死的。）

⚠️ **换品牌色时，原设计里"为什么选这个色相"的理由同时是约束。**
`@ops/design` 选靛蓝紫（278°）的理由是「与红/黄/绿色相距离最远，
永不被误读成状态色」。换成琥珀（73°）就撞进了原警告色（68°）的地盘 ——
主按钮和警告标记同色，人分不清「这是品牌元素」还是「这里有问题」。
必须把警告色一起挪开。只搬色值不看理由，就会复制出一个配色冲突。

守卫：`tooling/scripts/check-theme-override-layer.mjs`（已接进四个产品的 build）。

### 2.4 主题：`light-dark()` 只接受颜色参数

```css
/* ✅ 正确：包住完整的 oklch() */
--ops-accent-500: light-dark(oklch(0.54 0.19 278), oklch(0.56 0.19 278));

/* ❌ 错误：塞进 oklch 的亮度位 */
--ops-brand-l: light-dark(0.54, 0.56);
--ops-accent-500: oklch(var(--ops-brand-l) 0.19 278);   /* 整个值无效 → transparent */
```

**为什么**：`light-dark()` 只接受**颜色**参数。塞进 `oklch()` 的某个参数位，整个 `oklch()` 会成为无效值并**静默计算成 transparent**——表现是品牌色全站消失（logo、按钮、选中态全透明），而**控制台一条报错都没有，DOM 快照也完全看不出来**。这个坑实际踩过，只有靠截图才发现。

同理 alpha 位也不能用，要包住整个颜色值。

**推论**：任何"改完不报错但视觉不对"的问题，先截图，别看 DOM。

### 2.5 主按钮前景色必须自动选

`applyBrand()` 会按实际品牌色算出主按钮该配白字还是深色字，覆盖 `--ops-primary-foreground`。

**为什么**：写死白字是白标最常见的翻车点。客户品牌色若是亮黄，白字只有 1.4:1，而深色字有 13:1。按钮上的字能不能看清，比"看起来像个品牌按钮"重要得多。

**默认品牌色的亮度是实测定的，不要凭手感调**（`brand.test.ts` 锁着）：

| L | 主按钮前景 | 对比度 | 说明 |
|---|---|---|---|
| 0.54 | 白字 | 5.24 | 浅色主题取这档 |
| 0.56 | 白字 | 4.81 | 深色主题取这档 |
| 0.58 | 都不够 | 4.41 | **死区** |
| 0.62 | 深色字 | 4.89 | 能达标，但按钮会翻成近黑字 |

往上调会静默改变按钮文字颜色，不会有任何报错。

### 2.5.1 弱化文字的对比度也要达标，且必须两个主题一起测

> 🔴 **2026-08-20 实测更正**：原文「令牌共用所以一起过/一起挂」**不成立**。
> ops-cmdb v0.122 实测同一页面：深色挂 2 个、浅色挂 1 个，**三处没有一个是两边都挂的**——
> 两套主题的令牌是各自调过的。**必须两个主题分别跑一遍。**
>
> ⚠️ 检测脚本还有两个必踩的坑（详见
> `docs/ops-issues/clusters/platform-ops-cmdb/OPSCMDB-081-*`）：
> ① 令牌是 `oklch()`，正则抓 `rgb()` 会静默返回「0 个问题」——**用 canvas 转色**；
> ② **半透明背景必须做 alpha 合成**，否则同色半透明高亮（选中态、警告条底色）
>    会被判成「前景≈背景」，凭空多出一批假失败（我第一版就多报了 2 个）。
> ③ 脚本开头必须自检 `黑白对比度 === 21`，否则无法区分「没问题」和「没测到」。

`--muted-foreground` 这类"弱化"令牌是全站用得最多的前景色（表头、次要说明、
代码名、相对时间、角标），**它不达标 = 全站近一半文字不达标**。

要求：正文字号（< 18px）**≥ 4.5:1**，两个主题都要满足。角标等小字不得低于 **11px**。

⚠️ **两个主题用同一套语义令牌，所以它们会一起过、一起不过。**
只测一个主题、或只改一个主题的色值，都是无效的——要改的是令牌的亮度层级。

实测（ops-cmdb v0.82.0，同页 148 个元素）：

| | Light | Dark |
|---|---|---|
| 未达 4.5:1 | 65（44%） | 64（43%） |
| 表头 11.5px | 3.90 | 3.49 |
| `EE` 角标 **9px** | 3.90 | 3.49 |
| 次要文本 12px | 4.11 | 3.71 |

**怎么测**（必须这样测，别用正则）：

```js
// ⚠️ 本项目令牌是 oklch()，不是 rgb()。
// 用 /rgba?\(/ 抓 getComputedStyle().color 会一个都匹配不到，
// 静默返回"0 个问题"——看起来像全部通过。这个坑实际踩过。
const cv = document.createElement('canvas'); cv.width = cv.height = 1;
const ctx = cv.getContext('2d', { willReadFrequently: true });
const toRGB = (col) => { ctx.fillStyle = '#000'; ctx.fillStyle = col;
  ctx.fillRect(0, 0, 1, 1); return ctx.getImageData(0, 0, 1, 1).data; };
// 让浏览器自己做色彩空间转换，再按 WCAG 相对亮度公式算比值
```

**推论**：任何"看起来有点淡"的判断都不作数，必须量。
而任何返回"0 个问题"的检查脚本，先怀疑它根本没匹配到元素。


### 2.5.2 帮助文案里的每一个具体指引，都必须真实存在

本产品的文案质量整体很高，但一次全站验收里查出**三条指引指向不存在的东西**、
**三条说明描述了没实现的行为**：

| 文案 | 实际 |
|---|---|
| 证书页空态：去「域名与证书」菜单 | 该菜单不存在 |
| 变更影响面：「资源 ID **列表页每行都能拿到**」 | 没有任何列表页显示 ID |
| 数据源页：「要确认它通不通，**请点「测试连通性」**」 | 该按钮在**另一个页面**上，本页 11 行 0 个按钮 |
| 基础配置：飞书 Webhook 是「**全局兜底**的通知出口」 | 任务只看群列表，从不回落到它 |
| 注册商：`dry_run` 标着「预演模式」 | 全页无任何说明，看不出它影响哪些写操作 |
| 审计日志：「**只记写操作**」 | 实际把 MCP 只读查询也记了 |

**为什么这比没有文案更糟**：笼统的空态只是不帮忙；
**具体但错误的指引会让人确信有路可走，然后白找一圈**，
并且从此不再信任其它文案。第 4~6 条更严重——
它们描述的是**产品行为**，读者会据此做决定（以为提醒会发出去、以为续费不会真扣费、
以为查不到 AI 读了什么）。

**规则**：
1. 文案里出现**菜单名、按钮名、页面名**时，写的人要确认它当前存在且在同一页可达；
   不在同一页就给跳转链接，不要只写名字。
2. 文案里描述**行为**（"会兜底"/"只记 X"/"预演"）时，要么有测试钉住，
   要么不写。**行为描述和实现分叉时，没人会去改文案。**
3. 删功能、改菜单名、挪按钮时，`grep` 一遍文案里有没有提到它。

### 2.6 i18n

| 规则 | 为什么 |
|---|---|
| key 用英文语义命名，**不用中文做 key** | 改文案就得改 key，key 会散落在几十个文件里 |
| **后端只返回 error code + 参数**，前端翻译 | 后端拼好中文句子，英文界面就永远漏中文，且只在错误路径出现 |
| **组件库（`packages/ui`）不含任何面向用户的字符串** | 组件库一旦出现中文字面量，所有消费方都被污染 |
| 复数按各语言的 CLDR 规则 | 英文要 `_one`/`_other`，中文只要 `_other`。按字面比对 key 会把正确的语言包判成"多余" |
| 语言包 key **不能以 `_zero`/`_one`/`_two`/`_few`/`_many`/`_other` 结尾** | 它们是 CLDR 的复数类别，i18next 会把 `health.scaled_zero` 解析成"key=scaled 的 zero 形式"，那条文案运行时直接取不到。接口枚举保持蛇形（那是 API 契约），语言包 key 一律 camelCase，中间加一层映射 |
| 切语言必须同步 `<html lang>` | CJK 行高靠 `:lang(zh)` 生效，只切 i18next 不改 lang，英文界面会继续用中文行高 |
| 枚举值原样照搬（PROD/UAT） | 不要加"（生产）"这类解释括号 |
| 时间存 UTC，按用户时区显示 | 跨时区客户看到差 8 小时的时间戳，会怀疑整个系统的数据可信度 |
| 列表用相对时间，`title` 里给绝对时间 | 「3 天前」在排障复盘时推不回具体时刻 |
| CSV 导出中文要带 BOM | 否则 Excel 打开乱码 |
| 英文比中文长 30–50% | 按钮、表头、徽章不能写死宽度 |

`check-i18n.mjs` 和 `check-error-keys.mjs` 会在构建前校验完整性。

### 2.7 表格与密度

| 约定 | 为什么 |
|---|---|
| 数字列一律 `tabular-nums` | 数字宽度跳动是廉价感的头号来源，且几乎没人排查到这一点 |
| 表头 `sticky` | 长表格丢了列名，用户只能滚回顶部核对 |
| 超过 50 行虚拟化 | 再少虚拟化开销不划算，再多 DOM 节点拖慢滚动 |
| 选中行用**左侧 2px 色条 + 淡底**，不整行染色 | 整行染色会盖掉状态徽章的颜色，而那才是这一行最该被读到的信息 |
| 三档密度（32/40/48px），CSS 变量驱动 | 列表页要紧、详情页要松。一个密度走天下是"不专业"的直接来源 |
| 规格写数字（`8C 32G`），机型代号进 `title` | 没人记得住 `n2-standard-8` 是几核几 G，跨云厂商更没法比 |
| 多块盘**不要加总** | boot 96% + data 71% 加权才 79%，看着健康但系统盘要满了。而 DiskPressure 按单块盘判 |
| 明细列表按**严重度**排，不按字母序 | 人是来找"哪个不对劲"的；字母序会把唯一起不来的那个埋在第 40 行 |
| 外部系统的枚举值**原样显示**，不翻译 | `Running` / `CrashLoopBackOff` 是运维拿去 `kubectl` 里搜的词，译成中文就对不上了 |
| 带默认值的布尔列不能当"发生过"的证据 | `last_ok` 默认是 1，于是**从没执行过**的定时任务显示「正常」，而同一行的"上次执行"写着"从没跑过"——自相矛盾，且偏向"没问题"。要判"跑没跑过"，看时间戳 |
| 不认识的枚举值按**异常**处理，不按正常 | 当成正常，等于把上游新增的故障态静默放过 |

⚠️ 判严重度时别把**正常终态**算成异常：跑完的 Job Pod 是 `Succeeded`，
标红会让每个有定时任务的节点都像出了事 —— 而假故障看多了，真故障就没人看了。

**两处数据对不上时，两个数都摆出来**（节点自报 9 个 Pod、我们采到 4 个）。
挑一个显示就等于替用户断定哪份可信，而我们并不知道。

### 2.7.1 云资源与 K8s 分成两组菜单

**为什么不合成一个「资源」**：同一个词在两边指的是不同的东西——

| 词 | 云侧 | K8s 侧 |
|---|---|---|
| 网络 | VPC / 子网 / 防火墙 | Service / Ingress / NetworkPolicy |
| 存储 | 云盘 | PVC / StorageClass |
| 节点 | 一台虚机（在不在、多少钱） | 能不能调度、上面跑了什么 |

合成一个入口，就是把两个不同的东西压成一个名字，而点进去看到哪一种取决于我们
当时想给谁看——这正是全站在防的那类问题。两组的变更路径也不同（云控制台/IaC vs GitOps），
对象数量差一两个量级。

**「主机」与「节点」的对象重叠是故意的**，不是冗余：两页回答的是不同的问题，
互相链接即可（主机详情里已有节点关联三态；节点列表的「关联主机」列点开对应主机抽屉）。

⚠️ **两页对同一份数据的判断必须一致**。节点列表说"未接入"、主机抽屉说"节点上没有 Pod"
就是同一份数据两个答案，而看的人不知道该信哪个。
以 Pod 数为例，判据要抬到**集群**这一层：集群里有任意一行 Pod = 采集跑过了，
那么某个节点没有行就是真的没有；整个集群一行都没有，才是"没采过"。

⚠️ **节点状态要先看心跳再看它自称什么**。kubelet 停止上报后，`ready_status`
会停在最后一次的值上 —— 一个失联两小时的节点在库里仍然是 `Ready`。
只显示 `ready_status` 等于替一个联系不上的节点担保。
「失联」要独立成一档（不并进 NotReady）：NotReady 是它说自己没准备好，
失联是我们根本不知道。

### 2.7.1.1 分组的判据是「人来回答什么问题」，不是「东西是什么」

菜单分组最容易滑向两种错误的分法：**按对象类型**（域名一组、证书一组）
或**按供应商**（Cloudflare 的放一起、GCP 的放一起）。两种都错，因为
没人是带着"我要看 Cloudflare 的东西"这种念头打开系统的。

实际发生过的例子：CDN 站点最初被归到「平台服务」，理由是
"Cloudflare 和 Harbor 一样都是外部平台"——这是按供应商归类。
但没人早上起来想"我们用了哪些外部平台"，**天天有人在查"这个域名为什么 502"**。
于是它被移进「域名与入口」，和域名、DNS 解析、证书排成一条排障路径。

判据：**把这一组的名字念出来，它应该是一个人此刻想解决的问题**
（"外面怎么访问到我的服务"），而不是一个分类学名词（"外部平台集成"）。

推论：同一个对象出现在两组里是允许的，只要两组回答的问题不同
（主机 vs 节点就是这样）。为了"不重复"而硬塞进一组，反而会让两个问题
都答不好。

### 2.7.1.2 菜单超过约 20 项：折叠 + 命令面板

菜单是按权限过滤的，所以"长"这件事对不同角色差别极大 ——
实测同一套菜单：成本角色看到 4 项，管理员看到 43 项。
**先按角色数一下**，再决定要不要动，别凭管理员的观感就大改。

超过约 20 项时两件事一起做，缺一不可：

| 手段 | 解决什么 | 为什么单独不够 |
|---|---|---|
| 分组折叠（记住状态） | 菜单**变短** | 没让它变好找：你还是得逐组展开去猜 |
| 命令面板（⌘K） | 菜单**变好找** | 只有知道快捷键的人会用，而不知道的人最需要它 |

配套的四条细节，每条都对应一次会发生的困惑：

- **当前页所在的分组无条件展开**，但不改写用户存下来的偏好。
  从命令面板或深链跳进一个被收起的组时，高亮项看不见，人会以为自己不在菜单里。
- 收起的组里若含当前页，**标题旁点一个小点**——这是收起状态下唯一的位置线索。
- 命令面板里**只放当前用户看得到的页面**。放全量的话，没权限的人能搜到并跳进去，
  然后拿到 403 —— 等于把菜单过滤的意义抵消掉。
- 侧栏收成图标条时，每个图标**必须有 title**。只剩图标又没有提示的导航等于让人靠猜。

共享实现在 `packages/ui`：`useNavCollapse` / `useNavRail` / `CommandPalette`。
新系统直接用，不要各自实现 —— 各自实现的结果是每个系统的快捷键和记忆规则都不一样。

### 2.7.9 窄屏必须折叠侧栏，且要有断言钉住"页面不横向滚动"

AppShell 的桌面侧栏是固定宽（216px）。在 390px 视口下它吃掉 **55% 的宽度**，
内容区只剩 174px —— 实测（ops-cmdb v0.82.0，7 个代表页）**全部横向溢出 90~121px**：

```
说明文字每行只剩 1~2 个单词，竖排成一长条
面包屑折行、金额被右边界切断、页头按钮被挤出视口、顶栏用户区完全不可见
```

**这不是"有点挤"，是那一屏没法用。**

⚠️ **溢出元凶在每一页都是同一个元素（顶栏右侧用户区），
所以这是外壳的缺陷，不是业务页的**——
按 §2.7.5 所有产品都用同一个 AppShell，**它在每个 ops 产品里都存在，修一处全好**。

要求：

1. **加断点**：窄屏默认收起侧栏，改为汉堡按钮 + 抽屉浮层
   （「收起侧边栏」按钮本来就有，缺的是**按视口自动触发**）
2. **顶栏窄屏只留头像**，用户名/语言收进菜单
3. **页头操作按钮**窄屏下换行或收进 `⋯`
**断点建议**（ops-cmdb v0.82.0 实测：硬性最小内容宽度 **480px**，
低于它按 `480 − 视口` 线性溢出；768px 已无溢出但侧栏仍占 28%）：

| 视口 | 侧栏 |
|---|---|
| < 768px | 收起为汉堡 + 抽屉浮层 |
| 768 ~ 1024px | 图标条（约 56px） |
| ≥ 1024px | 完整侧栏 |

⚠️ **目标不是"别溢出"**：把最小宽度从 480 降到 390，
只是把"被截断"换成"极窄到没法用"（480px 时内容区只有 264px）。
**要折叠侧栏，不是压缩内容。**

**实现状态（2026-08-18）**：`@ops/ui` 的 `AppShell` 已支持，
通过 `responsive` prop 开启，断点由 `useNavViewport()` 判定：

```tsx
<SharedShell nav={NAV} can={...} brand={...} responsive t={t}>
```

⚠️ **默认 false，即保持原有行为**。规范说「修一处全好」，本该默认开启，
做成 opt-in 是因为已上线的产品要各自验证过窄屏再开 ——
上面第 2、3 条（顶栏窄屏收起用户区、页头按钮换行）需要产品自己配合，
不能被一次共享包升级顺带改掉布局。

**已开启**：ops-version（390 实测内容区 174px → 390px）。
**未开启**：ops-cmdb / ops-sso / ops-alert / ops-video-manager ——
各自验证过上面第 2、3 条之后加一个 `responsive` 即可，不需要写任何布局代码。

4. 🔴 **加断言**：几个代表页在 390px 下

   ```js
   document.documentElement.scrollWidth === document.documentElement.clientWidth
   ```

   这个检查极便宜，且**能永久钉住**——响应式问题的特点是
   "开发机上永远看不见"，只有断言拦得住。

⚠️ 排查纪律：**布局问题第一条命令永远是量 `documentElement`**。
只量内层滚动容器（表格的 `overflow-x:auto`）会得出"没问题"的结论，
因为撑破页面的那个元素在容器外面。

### 2.7.6 侧栏必须是**一列**，不许有"底部区"

分组从上到下顺序排列，没有例外区。

`@ops/ui` 的 `NavGroup` 上曾经有个 `footer?: boolean`，把「管理」类分组
挪出主列表、单独吊在侧栏最底下。**已删除，不要加回来。**

两个问题：

1. **位置不稳定。** 它和其它分组的距离取决于上面有多少组，
   而分组数量随权限变化——同一个菜单在管理员和只读用户那里位置完全不同，肌肉记忆失效。
2. **会被整段跳过。** 用户按"从上往下扫一遍"找菜单时，
   底部那组在视觉上不属于同一个序列，眼睛会直接掠过去。

需要弱化某组的存在感，就把它**排到最后一个**，而不是移出列表。
排最后已经足够表达"这些不常用"，同时保持一列的连续性。

⚠️ 这条被违反过一次（ops-cmdb 的「管理」组），用户反馈"之前不是统一一列的吗"。
所以 `footer` 字段已从类型定义里彻底删掉，而不是靠约定约束——
留着字段，下一个人还会用它。

### 2.7.7 列表行：破坏性操作收进 `⋯` 菜单，不做常驻按钮

用 `components/RowMenu`，不要在行上直接放 danger 按钮。

**理由不是"好看"：**

- 「删除」是列表里**最少用**的操作，却因为 danger 配色成了视觉最重的元素，
  而且通常紧挨着最常用的「编辑」——两者相隔几十像素、颜色还最扎眼
- 一行挂三四个按钮时行高被撑起来，每行重复同样的按钮文字，
  眼睛没法快速扫过数据本身。**数据是列表页的主体，操作是次要的**

**留在行上的判据**：高频、且当下就要用。
例如观测端点的「测试连通性」——配错地址的数据源和没配一样但界面看着是好的，
这个按钮比「保存成功」还重要，所以它留在行上；「编辑/删除」进菜单。

同理，时效性强的当下操作可以留在行上（如运行中任务的「取消」、审计详情里的「回滚」），
它们是那一刻的主操作，不是常驻在每一行的。

⚠️ 不要为了"少点一次"把删除放回行上。**删除本来就该多点一次。**

⚠️ 没权限 / 授权只读时**整个菜单不渲染**，不要渲染成禁用态：
禁用态会让人一直琢磨"为什么点不了"，而原因在菜单里没有位置解释
（行内按钮有 tooltip，菜单没有）。

### 2.7.7a 操作列固定在最右侧

列表页的操作列（`⋯` / 图标按钮）用 `meta: { action: true }` 标记，
`DataTable` 会把它 sticky 到右边。**所有产品统一这么做。**

#### 为什么统一，而不是"只给会横向滚的表"

一张表会不会横向滚，取决于窗口宽度、列内容长度、字号档位 —— 全是会变的。
按"现在滚不滚"决定要不要钉，等于让这件事随环境漂移：
**同一张表在窄屏上操作列不见了，而写代码的人在宽屏上看不到这个问题。**

旧版 CMDB 就是统一钉的（Element Plus 的 `fixed="right"`，几乎每个列表页都写了）。

#### 🔴 标记之后它必须**真的排在数组最后**

实测（1512px 窗口，不算窄）：

```
节点页 13 列，横向溢出 147px
列序：… 最后心跳 → (操作) → 实时用量
                            ↑ left=1805 > 可视区右边界 1728，整列在屏幕外
```

「实时用量」是在页面里 `...nodeColumns()` **之后追加**的，绕过了列定义文件。
于是被 sticky 钉住的其实是倒数第二列。Pod 页、集群页、数据源页都是同一形态。

⚠️ **"往列数组后面追加一列"是个很自然的写法**，没人会想到它破坏了操作列的位置。
守卫：`check-action-column.mjs`。

正确做法：**列的顺序只有一份真相，就是列定义文件里那个数组。**
需要页面状态的单元格（实时用量这种）把**渲染函数**注入进工厂，
而不是把**列**追加到工厂外面 —— 顺序归工厂管，内容归页面管。

#### ⚠️ sticky 单元格的背景必须跟着行态走

被钉住的格子要有不透明背景（否则滚动时下层内容透上来），
而背景色必须跟随行的状态（选中 / hover / 普通）：
固定一个色会让被钉住的那一格在选中行里显得"没被选中"，
而它和左边那些格子明明是同一行。走令牌，不要写死 —— 这个应用有明暗两套主题。

### 2.7.7b 纯图标按钮：只给"公认图标的只读操作"，且必须能说明自己是什么

行内按钮文字太长会把一行挤满，但**不是所有操作都能变成图标**。

**可以图标化**（三个条件全满足）：只读 · 高频 · 图标语义公认
—— 下载 ⬇ / 同步刷新 ↻ / 测试 ⚡ / 看日志 📄 / 变更历史 🕘

**绝不图标化**：

| 类 | 为什么 |
|---|---|
| 破坏性（删除、踢下线） | 收进 `⋯`，见 §2.7.7 |
| **会花钱**（续费） | 比删除更严格：删除还能从备份恢复，**扣费不能撤销**。P0-9 刚把「续费」从紫色主按钮降级过，图标化等于又把它变得更容易误点 |
| 语义特殊、没有公认图标 | 如「DNS 验证已就绪」。变成图标后只能靠 hover，而**触屏上没有 hover** |
| 工具条主按钮（新增/接入） | 那是这一页的主动作，要一眼看见 |

⚠️ **一行里并排三个图标，比并排三个文字更难扫** —— 人得逐个 hover 才知道是什么。
行内最多留**一个**图标按钮（主操作），其余收进 `⋯`。

**硬性要求**：`iconOnly` 必须同时给 `aria-label`（读屏 + 测试定位）和 `title`（鼠标 hover）。
守卫 `check-icon-buttons.mjs` 会拦。

🔴 **守卫查不出的那种**：包装组件把 `title` 覆盖掉。
`WriteButton` 曾经写 `title={reason || undefined}` 且排在 `{...rest}` **之后** ——
能点的时候把调用方传的 title 抹成 undefined。源码里 `title=` 明明写着、守卫也是绿的，
**只有真的 hover 一下才看得见**。包装组件转发 title 时一律用合并而不是覆盖。

### 2.7.7c 字段取回来了就得有人读，不然别取

`queries.ts` 里声明并映射的每个字段，**必须至少有一处读它**
（`x.field` 属性访问 或 `{ field }` 解构）。

反例（真事，旧版 CMDB 的 Pod IP 列就是这么丢的）：

```ts
// queries.ts
podIp: string             // 类型声明了
podIp: raw.pod_ip ?? ''   // 映射也取了
// columns.tsx —— 零处引用，界面上根本没有这一列
```

🔴 这类缺陷**看代码像接好了**：复查的人打开 `queries.ts` 看到字段在、映射在，
就不会再往下翻渲染层。它同时躲过了三个已有守卫：

- `check-read-coverage` 只管路由级 —— 路由调了
- `check-field-usage` 只管字段名搜不搜得到 —— 映射那行就有
- `check-field-names` 只管名字对不对 —— 名字是对的

守卫：`check-dead-fields.mjs`。**映射写入不算"读"** —— 算上它就退化成
`check-field-usage`，一条都抓不到。

三条出路，选一条，没有第四条：

| 情形 | 做法 |
|---|---|
| 真该显示 | 渲染它 |
| 后端本来就不该给 | 从类型和映射里删掉，别留着骗人 |
| 有正当理由不显示 | 进 `ALLOW`，**写清楚理由** |

⚠️「暂时没空做」不是理由。那种要先建档，再挂进 `FILED` 并注明档号，
**修完必须把那一条删掉** —— 留着等于把那个位置永久豁免。

⚠️ 一类必须逐条确认、不能整类豁免的：后端同时给了数字和人话
（`filtered_out` 与 `empty_reason`），显示人话那份是对的。
但"有个字符串在显示"不等于"那个字符串包含了这个数字"。

### 2.7.7d 写接口收得下的字段，界面上就得能改

后端 handler 的请求体里每有一个字段，前端就必须有地方把它发出去。

反例（真事，ops-cmdb 定时任务）：

```
后端 PUT /api/scheduled-tasks/:key  收 5 个
    schedule / notify_enabled / lark_group_id / notify_when / at_user_ids
前端 只发  { enabled: 0|1 }
```

「改执行频率」「配飞书通知（开关/群/时机/@谁）」五件事后端全做好了、
旧版界面上全都有，新版一件也做不了。

🔴 **路由有人调 ≠ 字段都发了。** `check-write-coverage` 守的是路由级，
只要有人调过一次就绿 —— 字段这一层此前没有任何守卫。

守卫：`check-write-fields.mjs`。它的语料**只取可能构造请求体的地方**
（`useMutation(...)` 整块 + `*Input/*Payload/*Req/*Body` 接口）。
拿整个前端去搜键名会恒绿 —— 响应类型里也有同名字段。

⚠️ 顺带一条后端规矩：把新字段加进已有的 Update handler 时，
写失败必须返回错误。真出现过 `_, _ = h.DB.Exec(...)` 后面照样
`c.JSON(200, {"ok":true})` —— 保存成功了但没存上，
正是"出错时必须看起来像出错"要杜绝的那种形态。

### 2.7.8 列表页用表格，不要裸 `div` 排版

有表头才知道每一列是什么。没有表头时，一串灰色小字读者只能猜，
而且没法按列纵向扫描比较。

⚠️ 更实际的后果：裸 div 排版时，作者会自然地"只放看起来重要的字段"，
于是关键配置被漏掉。观测端点页就是这样——**环境和集群隔离标签根本没显示**，
而这两个恰恰决定了这个数据源会被谁用到，配错了在列表上完全看不出来。
表格强制你为每个字段决定"要不要一列"，漏掉是显式的选择而不是无意识的省略。

### 2.7.5 应用外壳必须用 `@ops/ui` 的 AppShell，产品不许自己写

产品只提供三样，**外壳本体不许再写一份**：

```tsx
<SharedShell
  nav={NAV}                       // NavGroup[]，各产品自己的 layouts/nav.ts
  can={(perm) => hasPerm(...)}    // 权限判据；没有 RBAC 就显式写 () => true
  brand="OpsPlane" version={__APP_VERSION__}
  t={t}
  {...rest}
/>
```

样板：`ops-cmdb/frontend/src/layouts/AppShell.tsx`（66 行）。
守卫：`tooling/scripts/check-shell-consistency.mjs`。

#### 2.7.5.1 为什么这条必须由守卫拦，而不是写进文档就行

分组判据（§2.7.1.1）和折叠规则（§2.7.1.2）**早就写在这份文档里**，
但三个产品照样各写了一份外壳：cmdb 351 行、alert 394 行、sso 87 行。

代价不是"长得不一样"，是**能力分叉**：
ops-alert 那份是从 cmdb 抄过去再改的，抄的过程中漏掉了权限过滤 ——
菜单不按权限收，用户点进去才拿到 403。

> 复制粘贴出来的第二份代码，从复制那一刻起就开始漂移，
> 而没有人会在改第二份的时候回头对照文档。

所以拦截点不能是文档，只能是**「根本不存在第二份」**。
文档负责解释为什么，守卫负责保证做到 —— 两者缺一不可，但顺序不能反。

#### 2.7.5.2 守卫本身不许写死产品清单

三个守卫曾各写着一份硬编码的产品目录清单，旁边还写着注释
「新产品加进来时补一行」—— 而 ops-alert 建出来之后一行都没补。

后果是：**那个产品完全不受任何守卫约束，而守卫照样打印「✓ 全部通过」。**
一个只检查部分产品的守卫比没有守卫更危险，它的绿色会被当成"全都查过了"。

清单必须是**推导出来的**，不是维护出来的：统一用
`tooling/scripts/lib/products.mjs` 的 `products()` / `frontendDirs()`。
接上之后立刻在 ops-alert 查出 2 个不存在的 i18n key、
在 ops-sso 查出 7 处硬编码颜色 —— 那些问题一直都在，只是没人扫到。

#### 2.7.5.3 判据要贴着"要拦的东西"，不是贴着"容易写的正则"

外壳守卫第一版的判据是「文件里出现 `<aside>`」，立刻误报三个页面：
详情面板、模拟器面板、登录页左半屏都合法地用了 `aside`。

改成「导出名为 `AppShell` / `Shell` 的组件」之后误报归零。
**天天误报的守卫会被人直接关掉，那比没有守卫更糟。**

### 2.7.2 每个列表页都必须有分页条

**这不是"省得滑动"，是防静默截断。**

前端传 `size=50`，后端就只返回 50 条 —— 而页脚还写着"共 61 条"。
界面上没有任何迹象表明还有 11 条没显示：不报错、不留白、不置灰，
排障的人就照着这 50 条下结论了。实测撞到过：服务页 61 条只画了 50 条，
Pod 页 51 条只画了 50 条，而我做完这些页面时以为它们是完整的。

统一用 `<Pagination>`，规则：

| 规则 | 为什么 |
|---|---|
| **吸底**（`sticky bottom-0` + 实底色） | 放在内容流末尾的话，看"共几条"要先滚三屏 —— 而它恰恰是用来避免滚动的。同表头 sticky |
| 总数没超过一页也要显示「共 N 条」 | 这句话是个**断言**：你看到的就是全部。没有它，用户分不清"只有 12 条"和"被截断到 12 条" |
| 页码与每页条数**进 URL** | 分享出去的链接要落到同一页；刷新也不跳回第一页 |
| `size` 在服务端和前端都要**夹上限** | URL 是用户能改的，`size=100000` 会把后端拖垮 |
| 改每页条数后回第一页 | 停在第 5 页而新页数只有 2 页，用户看到空列表会以为数据没了 |

⚠️ 后端**没有分页能力的接口不要在前端假装分页**（切数组）：那样总数是对的、
翻页也能点，但每次都在重新拉全量 —— 到万级时页面直接卡死，而症状只是"有点慢"。

### 2.7.3 老接口的 `200 + {ok:false}` 必须当成失败

仓库里有一批接口（测连通、立即同步这类动作）**成功失败都返回 HTTP 200**，
差别只在响应体的 `ok` 字段。客户端只看状态码的话，失败会被渲染成成功。

实测撞到过：三个**根本没有 kubeconfig** 的集群，点「测试连通性」全部显示绿色的
「连通」——后端明明回的是 `{"ok":false,"error":"未配置连接方式"}`。

⚠️ 测连通按钮存在的唯一意义就是告诉你通不通。**它撒谎比没有这个按钮更糟**：
没有按钮时人还会去别处确认，绿灯亮着就不会了。

动作类请求一律走 `apiAction()`，它把 `ok === false` 也抛成 `ApiError`。
失败时**把后端给的 error 原样显示**——「连不上」没法处置，
「未配置连接方式（kubeconfig 或 GKE 云账号）」一眼就知道去干什么。

### 2.8 筛选器用下拉，不用平铺分段控件

**为什么**：分段控件每多一个选项就多占一截横向空间。筛选维度一多（状态 + 集群 + 机型 + 搜索框）一行就放不下，换行后工具栏高度会随筛选条件数量跳变。下拉是定宽的，加多少个都不挤。

收起态显示「标签：值 计数」（`状态 全部 8`），只显示值的话一排下拉分不清哪个是哪个维度。

**偏好类设置（主题/语言/密度）收进一个图标弹出**，不常驻工具栏——它们是"设一次就不再碰"的东西，不该和搜索、刷新这类每天点的抢位置。且**改完立即生效、立即持久化，不要保存按钮**（偏好加保存按钮只会让人以为没生效而反复点）。

**右上角用户区显示头像 + 用户名**，不是只放头像：运维平台常有多账号切换（自己的号/值班号/只读号），只有头像得点开才知道当前是谁，而用错账号做写操作代价很高。

### 2.9 弹层

- **Popover / 下拉菜单**：点外部关闭、Esc 关闭、关闭后焦点归还触发器。
- **Dialog / 确认弹窗**：**禁止点遮罩关闭**（`close-on-click-modal=false`），只能点关闭/X/保存。

**为什么两者不同**：dialog 里有未保存内容，误关代价高；下拉菜单没有待提交状态，点外面收起是所有人的预期，强迫去点关闭按钮反而别扭。

**禁止浏览器原生弹窗**（`window.confirm` / `alert` / `prompt`），统一走应用内的确认组件。

### 2.10 权限

- **前端只做显隐，拦截全在后端。**
- 权限判据一律以**后端返回的 `is_admin`** 为准，前端禁止按登录来源之类自行推导（这条栽过三次）。
- 无权限的页面显示**缺哪个权限码**，不是空白。
- 菜单只有一份数据源（`layouts/nav.ts`），权限过滤也在这一处。
- 未实现的菜单**置灰保留**，不要直接不渲染——不渲染会让人以为功能不存在。
- 权限**每次进应用从 `/api/me` 现取**，不用登录时那份缓存：角色会在服务端被改，
  缓存那份会让菜单显示着、点进去 403，看起来像系统坏了。
- 菜单项的 `perm` 必须与后端 `perm.go` 里的码**同名**；写错不会报错，
  只会让该菜单对所有非管理员静默消失（管理员全放行，自己看不出来）。
  `check-perm-codes.mjs` 两个方向都核对。
- **权限没到手时不渲染菜单，也不渲染页面内容**（显示骨架 / `null`）。
  先渲染再撤下会闪一帧不该看到的入口和数据，而那一帧截得下来。

⚠️ **「权限取失败」绝不能渲染成「没有权限」**。两者界面上一模一样，
但用户的下一步完全相反：一个该找管理员要权限（而管理员会发现他明明有），
一个该去看服务端还活着没有。所以权限查询要按 **加载中 / 失败 / 拿到了** 三态处理，
失败走带重试的错误态。

⚠️ **建账号必须同时落租户归属**。登录时查不到归属会回落到默认租户并照常发会话，
而请求时的租户中间件按 `user_tenants` 严格校验 —— 两边判据不一致，
结果是账号登得进去、每个接口 403，而"租户"是建号的人从没碰过的概念。
补历史数据的逻辑要**独立、幂等、每次启动都跑**（写在"首次初始化"分支里，
对已存在的安装永远不会执行：全新部署一切正常，升级上来的库继续全 403）。

### 2.11 凭据、标识与外链

#### 密码框一律带「显示」按钮

任何 `type="password"` 的地方都用 `@ops/ui` 的 `PasswordInput`
（各产品再包一层拿 i18n 文案，如 ops-sso 的 `shared/Pwd.tsx`），
**禁止直接写 `<input type="password">`**。

**为什么**：圆点回显把「密码错了」和「密码打错了」变成同一个现象，
而这两件事的下一步完全相反——一个去找管理员重置，一个把多打的空格删掉。
实测踩过：登录失败排查半天，最后是大小写打错一个字母。

三个容易漏的细节，组件里已经处理，自己造轮子时必踩：

- `tabIndex={-1}`：Tab 要从密码框直接跳到提交按钮。夹一个眼睛按钮，
  习惯键盘的人会多按一次且不知道焦点去了哪。
- `aria-label` **随状态变**（显示口令 / 隐藏口令）：图标按钮对读屏软件是空的。
- `type="button"`：不写的话在 form 里点一下就把表单提交了。

#### 「只显示一次」的密钥：不能自动关屏

密钥明文只在创建响应里出现一次（库里存哈希）。所以：

- 拿到密钥后**停在结果屏**，由人点「我已保存」才收起。直接关掉表单 = 密钥丢了，
  补救只能重建，而重建会让对方系统里已填好的配置作废。
- 这一屏的密钥**故意明文显示**，不要用圆点盖住——这一屏的全部目的就是让人拿到它。
- 配「复制」按钮，且**复制失败要说出来**。以为复制成功、粘贴发现是旧内容，
  比「按钮没反应」难查得多。
- 密钥**绝不写进审计日志**。

#### 标识类的值由系统生成，不让人填

`client_id` 这类「公开但可枚举」的标识，一律后端生成，表单上只写一句
「建的时候自动生成」。

**为什么**：让人填，填出来的一定是 `harbor` / `prod` / `test` 这种好记的值，
而好记等于好猜。标识本身不是机密，但可枚举的标识让攻击者省掉侦察那一步。
形状对齐 Auth0 / Okta：`client_` + 22 位 base62（约 131 位熵）。

⚠️ 用 base62，不要 base64：这些值会出现在 URL 查询串、配置文件和日志里，
`+` `/` `=` 在那些地方要转义，而转义过一次的值和原值比对不上。

同一个东西如果有两条创建路径（例：接入应用时顺带建 / 在客户端页单独建），
**必须共用同一个函数**。各写一遍迟早分叉，而分叉的表现是
「从 A 路建的能用、从 B 路建的不能用」，极难查。

#### 跳出本站的链接一律新标签页

门户磁贴、外部系统入口这类链接：`target="_blank"` + `rel="noopener noreferrer"`。

**为什么**：原地跳走等于把本站从历史里换掉，人回来还要重新进一次。
`rel` 两个值都不能省——`noopener` 挡住目标页通过 `window.opener` 反向操作本页，
`noreferrer` 不把本站地址泄给外部系统。

⚠️ 只给**能点开**的链接加 `target`。渲染成「需申请」的磁贴点了不该开新标签页，
否则会开出一个空白页，看起来像系统坏了。

## 3. 后端

### 3.1 列表接口的统一约定

```
GET /api/v1/hosts?page=1&size=50&sort=-cost&status=running&q=kafka

{
  "items": [...],
  "page": 1, "size": 50, "total": 412,
  "facets": { "status": {"running": 347, "stopped": 12, "destroyed": 53} }
}
```

用 `internal/httpx` 的 `BindPage` / `NewList` / `WhereBuilder`，不要各写各的。

| 规则 | 为什么 |
|---|---|
| **`facets` 按「不含维度筛选」统计** | 选了 `status=running` 后，下拉里"已销毁"仍要显示 53。若按筛选后统计就全是 0，用户看不出"切过去还有多少台"——而那正是下拉里数字的意义 |
| **`items` 绝不为 nil** | nil 序列化成 `null`，前端 `.length` 抛异常。**只在结果为空时发生**，有数据时一切正常，最容易漏测 |
| **排序字段必须白名单** | 直接把参数拼进 SQL 就是注入：`sort=name;DROP TABLE hosts--`。白名单让"能排哪些列"是服务端的决定 |
| **只接受声明过的筛选键** | 前端拼错参数名（`cluter=`）会静默失效，而界面看起来筛选生效了 |
| **`size` 必须有上限** | 没有的话一个 `size=1000000` 就能把内存打满 |
| **分页参数写错退回默认值，不报错** | 用户看到"翻页没生效"，比看到一个 400 错误页强 |
| **越界页码返回空列表**，不退回最后一页 | 退回最后一页会让"下一页"按钮看起来永远可点 |
| **排序在服务端** | 前端只有当前页数据，排出来的"最贵的机器"是当前页里最贵的 |
| LIKE 搜索要转义 `%` 和 `_` | 用户搜 `50%` 会变成通配符，"搜出一堆不相关的"没人想得到是转义问题 |

**例外要标注**：如果某个接口因为字段是应用层计算的（如成本估算）而必须先取全量再内存分页，**在代码注释里写明它是局部妥协，并说明什么规模下不能照抄**。

**分页方式按对象规模选，不按"上一个页面怎么写的"选**：

| 规模 | 做法 | 例子 |
|---|---|---|
| 十几~几百 | 全取到内存，纯函数筛选/排序/分页（好写、好测） | 集群、节点 |
| 万级以上 | **分页、筛选、分面全部在 SQL 里做** | Pod、事件、审计 |

照抄内存分页去做十万级列表，表现是"页面转圈"和内存被打满 ——
而没人会立刻联想到是分页方式的问题。所以内存分页那份**必须在注释里写明规模上限**。

⚠️ SQL 侧做分面时，每个维度仍要**排除它自己那一条筛选**，且必须全量统计。
按当前页统计出来的数字看起来完全正常，但它是错的。

### 3.2 错误响应

```json
{ "code": "upstream_timeout", "message_key": "error.upstreamTimeout",
  "params": {"cluster": "g32-prod"}, "request_id": "8f2a91c3" }
```

用 `httpx.Fail(c, httpx.CodeUpstreamTimeout, err, params)`。

- **不返回给用户看的句子**，只返回 code + 参数。
- `message` 字段是**给运维看的英文技术描述**，前端不展示给终端用户。
- 错误码 → HTTP 状态码的映射集中在一张表里。同一个错误在不同 handler 返回不同状态码，前端的重试策略就没法统一。
- **新增错误码必须同步在前端语言包补文案**，`check-error-keys.mjs` 会校验。

### 3.3 数据语义：NULL / 0 / 空数组是三件事

| 值 | 含义 |
|---|---|
| `NULL` | 没采到（数据源没配、采集失败、字段对不上） |
| `0` | 真的是 0 |
| `[]` | 确认没有（已销毁的机器，盘跟着删了） |

**绝不用 0 或 -1 当哨兵值**：没采到的会被算进平均值，把整体用量算低；前端也没法区分该显示「未接入」还是「0%」。

**Go 侧用指针表达 NULL**，且要加 `omitempty`：

```go
UsedPercent *float64 `json:"used_percent,omitempty"`
```

**为什么加 omitempty**：Swagger 2.0 没有 nullable 概念，生成出的 TS 类型是 `used_percent?: number`（optional）。若 nil 时仍输出 `null`，类型与实际就对不上——编译期看着没问题，运行时拿到 null 做算术会得到 0，把「没采到」变成「空盘」。

### 3.3.2 判定阈值必须由被判对象**自己的周期**推导，不能全局写死一个数

本项目已在**四个不同地方**踩过同一个坑：**判定阈值 ≈（或小于）信号本身的更新周期**。

| 出处 | 信号周期 | 阈值 | 后果 |
|---|---|---|---|
| OPSCMDB-025 | 取整粒度 5min + 采集 2min | 5min | 16 台节点里 8 台常年"失联" |
| OPSCMDB-027 | `conditions[Ready]` 上报 5min | 5min | 修了三个版本仍有 2 台误报 |
| 凭据管理 / 数据源页 | `host_sync` **每天 03:00 一次** | 固定小时数 | GCP **每天约 22 小时**被判"同步停摆" |
| 事件中心 | — | `limit: 500` | 超过后 `truncated` 无人读，静默截断 |

第三条尤其能说明问题：巡检页说 `host_sync`「● 正常」，
凭据管理页对**同一次同步**说「配了凭据但同步停摆，早该同步了却没有」。
**两页对同一个事实给出相反结论，而"停摆"那一页是错的。**

> **推论**：这类缺陷不能按页面修。
> 「某个信号是否过期」应当只有**一处实现**，所有页面调它；
> 而那一处实现要从任务自己的 cron / `next_run` 推导，不接受调用方传阈值。
> 判据只要能被复制粘贴，就一定会被复制到下一个页面。

### ⚠️ 排查这类问题时先确认「两个页面读的是不是同一个字段」

2026-08-20 我在 ops-cmdb 上差点把一条不成立的案例写进上表：
主机页 `LAST SYNC` 显示 13 小时前（`synced_at`，云同步时刻，每天 03:00），
总览页 Data freshness 显示 12 小时前并标 stale（`freshness.hosts`，
记录最后写入时刻，被 30 分钟周期的采集任务刷新）。

**两个字段语义不同、周期不同**，我却按"同一个事实两页不一致"去判，
结论（阈值选错）因此站不住。49 分钟后再看，总览页已变成「19 秒前」。

> **规则**：判定"两页不一致"之前，先确认它们**声称描述的是不是同一件事**。
> 对时间类指标，**单次观测不足以定性** —— 至少在两个时刻各看一次。

**规则**：

```
容忍窗口 = f(该对象自己的调度周期)          ✅  如 2×周期 + 余量
容忍窗口 = 全局常量 STALE_AFTER            ❌  周期不同的对象必然有一半误报
```

- 每类数据源/任务把**自己的周期**存下来（cron 表达式、续约间隔、上报频率），
  判定时读它。
- 阈值和周期是**同一个不变式的两端**，必须写在一起或干脆消除耦合
  （OPSCMDB-025 的解法是把判定挪到采集时刻，耦合就不存在了）。
- **回归测试要钉死这个数学关系**，不是钉死某段代码
  （见 `k8ssource/zz_heartbeat_stale_test.go`）。

⚠️ **强信号**：对称的异常分布（正好一半失联）、
或"常年固定比例告警"，先怀疑判据，别去查对象。

### 3.3.3 `0` 表示"不限"时，全站必须用同一种呈现

`audit_retention_days = 0` 在本产品里表示**永不清理**（= 无限）。
但同一个 0：

- 基础配置页：正确说明「填 0 的意思是永不清理，不是立刻清理——**两个理解方向正好相反**」⭐
- 授权页：渲染成「—」（读起来像"没数据"），**且不参与容量超限判定**
  （授权上限 3650 天，实际是无限，`exceeded` 却是空的）

**规则**：值域里出现"0 = 不限/无限"时，
① 接口层给一个显式布尔或枚举（`unlimited: true`），不要让消费方各自解释 0；
② 校验逻辑必须把"无限"当成**超过任何有限上限**处理，不能因为取不到数就跳过；
③ 界面统一显示「不限」，不显示 `0`、更不显示「—」。

（相关历史：授权模块出过"永久（零值）被判过期"的 bug，同一族问题。）

### 3.4 状态字段：不要覆写真值，另出派生字段

已销毁的机器**不能靠改 `status` 来表达**。同步时发现云上查不到只置 `stale=1`，`status` 停在最后一次同步到的值上，另出一个 `lifecycle`（present/gone）供展示层用。

**为什么**：
1. `TERMINATED` 在云厂商语义里是"已停机、实例还在、磁盘还计费"，借用它会把"销毁"和"关机"混成一个值——而前者不花钱、后者还在花钱。
2. `stale` 是**推断**（同步时没返回 ≠ 一定销毁，也可能同步本身坏了）。覆写掉真值，一旦误标就再也查不到最后一次观测到的真实状态。

**通用原则**：**观测值和推断值分开存**，展示层用推断值，观测值留作证据。

### 2.5.3 有外部副作用的按钮，把后果写进文案里

2026-08-20 在 ops-cmdb 域名页看到的做法，值得全站沿用：

```
[Sync now]  [Auto-link modules]  [Add domain]  [Renew (charges money)]  [Renewal history]
                                                       ^^^^^^^^^^^^^^^
```

**「会扣钱」直接写在按钮上。** 用户在点之前就知道后果 ——
不依赖二次确认弹窗（可能被连点跳过），也不依赖文档（不会有人去读）。

对照同一产品证书页的三个按钮：

```
[Expiry inspection]  [ACME accounts]  [Request certificate]
```

三个都是无 `title`、无 `aria-label` 的 `<button type="button">`，
**从界面和 DOM 上都分不出哪个是只读、哪个会向外部发起请求**。
（其中 `Expiry inspection` 其实是纯 `apiGet`，
而 `Request certificate` 会真的去 ACME 签发 —— 验收时只能靠读源码区分。）

**规则**：按钮的外部副作用属于**用户在点击前必须知道**的信息，
应当出现在按钮文案或其紧邻的说明里，而不只在确认弹窗里。至少覆盖三类：

| 副作用 | 建议标注 |
|---|---|
| 产生费用 | `(charges money)` / `（会扣费）` |
| 向外部系统发起写请求 | `(calls provider)` / `（会调用厂商接口）` |
| 不可撤销 | `(irreversible)` / `（不可撤销）` |

⚠️ 反过来也成立：**纯只读的操作也值得标出来**，
否则用户会因为不确定而不敢点，工具的价值就打了折
（本轮我为确认一个按钮是否只读，专门去读了它的源码）。

### 3.3.4 异步操作的审计结果不能记成「成功」

HTTP 202 / 「已提交」/ 「已触发」表示**请求被接受**，不表示**操作成功**。
把它记成 `success`，会让审计里一条最终失败的操作永远显示为成功。

ops-cmdb 的做法（2026-08-20 实测，可直接照抄）：

```
RESULT: accepted
        "Accepted — outcome unknown yet. Check the run history under Scheduled tasks."
```

**独立状态 + 说明「结果尚未可知」+ 指出去哪儿看最终结果。**

配套：审计详情里对「没有 before/after 可比」的操作，
要说明**为什么**没有，而不是渲染成空或「—→—」：

```
This kind of operation does not modify a single row, so there is no before/after to compare.
It acts on an external system (registrar, DNS, CA) or is a trigger action;
see the endpoint result above and the run history.
```

⚠️ 「—→—」这种渲染最危险：它看起来像**有变更但值都是空**，
而实际是**这类操作根本没有行级变更**。两者含义完全相反。

### 3.3.5 审计要声明自己**不记**什么

同一处的范围说明，值得全站沿用：

```
Scope: every write operation, plus every AI call via MCP — including read-only queries,
       because what the AI took must be traceable.
       Humans browsing read-only pages is not recorded,
       so not finding "which page someone viewed" is expected.
```

三件事一次说清：**记什么** / **为什么某类只读也要记** / **查不到什么、且那是预期内的**。

**第三点最容易被省略，也最重要** —— 没有它，用户在查不到某条记录时
无法区分「审计漏了」和「本来就不记」，于是整个审计的可信度都被怀疑。

> 这与三态纪律同源：**「没有」与「不适用」必须可区分**，审计层面也一样。

### 3.4.4 后端算出来的字段，必须有人消费——否则等于没算

一次 46 页全站验收里，**「后端算了/采了、前端没接」出现了 17 次**。
这是本项目**最高频的单一缺陷类型**，远超任何具体 bug。

典型（每条都是后端已有字段、界面上完全没有）：

| 后端字段 | 本该出现在 |
|---|---|
| `rule_note`（告警摘要，279 条里 273 条非空） | 告警列表（界面整列渲染成「—」） |
| `object`（告警对象） | 告警列表（47 条不同对象显示成 47 行相同文字） |
| `upcoming: 5`（即将到期） | 事件中心（整页唯一"还来得及处理"的信息） |
| `truncated`（是否被截断） | 事件中心（超过 500 条后会**静默**给残缺列表） |
| `cpu_wasted_cores` / `suggest_cpu_req_m` | 闲置与浪费（页面标题就叫这个） |
| `unpriced_hosts` / `destroyed_excluded` | 成本总览（判断总额可不可信的依据） |
| `created_by` / `created_at`（MCP 令牌） | AI 接入（能读全库的令牌，谁批的） |
| `has_cred` / `sync_supported` | 注册商 |

**为什么危害大于"少个字段"**：

1. 很多字段是**可信度信息**（`truncated` / `unpriced_hosts` / `stale_reason`）。
   不接它们，等于把"这个数不可信"的信号丢掉，只留下一个干净的数字。
   —— 这是[§3.4.3 页面级"没采到"必须区别于"确实没有"] 在展示层的翻车。
2. 后端作者以为已经交付了，前端作者不知道有这个字段，**双方都不认为自己漏了东西**。

**规则**：

- 新增接口字段时，**同一个 PR 要么接线，要么在字段旁写注释说明谁会消费它**。
- 契约测试要覆盖"字段有值时界面能显示"，不只是"接口返回了字段"。
- Review 时对着接口响应逐字段问一句"这个谁用"。
- **可信度类字段（`*_stale` / `truncated` / `*_reason` / `unpriced_*`）
  一律视为必接**，不接就是把三态压回两态。

⚠️ 反面参照：`/api/mcp/info` 返回 `tools_licensed: 87, tools_total: 87`，
界面显示「当前可用 87 个，产品共 87 个」——**双计数让"是不是被限制了"一眼可见**。
这是本项目里把后端计算正确接线的最好例子，分档类信息都该这么做。


### 3.4.1 授权（license）落地

完整规范见 [LICENSING.md](LICENSING.md)。这里只记**接入时最容易漏掉、且漏了不报错**的几条：

| 规则 | 为什么 |
|---|---|
| 装载用 `LoadAt` 不是 `Load`，且库里有 `mismatch_since` 列 | `Load` 会退回"从到期日起算宽限期"的旧规则。那条路径下**进程每重启一次宽限期就重置一次**，等于永久宽限 —— 而状态一直显示"宽限期内"，没有任何迹象表明防线没工作 |
| 写 `mismatch_since` 必须带 `WHERE mismatch_since IS NULL` | 不加就是每次装载都刷新它，效果同上 |
| 换授权时把 `mismatch_since` 清空 | 新授权是照当前指纹签的，留着上一份的时刻会让它一装上就已经在宽限期里 |
| 指纹的两个输入都取自**数据库** | 取宿主机 MAC/hostname 的话，多副本下每个 Pod 算出的指纹不同，表现是「重启后偶发提示未授权」，只在一部分请求上出现 |
| 起 `Watch`，`OnWatchError` 必填 | 不起：管理员在 A 副本激活，B/C 停在旧状态直到重启，现象是「激活了但一半请求仍报未授权」。留空 `OnWatchError`：同步错误被静默吞掉，某个副本永远停在旧值 |
| 「查不出来」与「确认没有」严格分开 | 前者保持原状，后者才 `Clear()`。混为一谈的话，数据库抖一下就把全公司的授权吊销了 |
| 只读降级**只拦写接口** | 把读也锁掉，客户连自己的数据都导不出来 —— 那不是催款是扣押 |
| 恢复授权本身要用的写接口必须放行 | 登录、贴激活码。不放行的话，过期之后连自救的路都没有，客户付了钱也只能找我们改库 |
| 装载失败**不阻止启动** | 退回 CE 档即可。让服务起不来，是把"数据库抖了一下"放大成一次全站故障 |
| 只读降级挂在权限校验**之后** | 没权限就是没权限，不该被告知"系统只读" —— 那会让人以为续了费就能做 |

⚠️ 验证这套东西**必须真的走一遍**：签一份指纹对不上的授权装进去，确认状态是
`finger_mismat` 而不是过期、`mismatch_since` 落了库、**重启后它没被刷新**。
最后这一格才是防线成不成立的判据，而单测覆盖不到（它测不了"重启"）。

⚠️ **签发台拒绝签发已过期的 license**（"签一份出生即过期的没有意义"）。
所以 `grace` / `expired` / `lapsed` 三态**没法用真授权在界面上复现**——
它们靠纯函数单测锁住（七态文案两两不同、色调分三档），
别为了截图去改签发台的校验。

界面侧还有三条：

| 规则 | 为什么 |
|---|---|
| 授权页**任何登录用户都看得到**，只有激活框按权限显隐 | 过期只读时，普通用户看到的是一堆莫名失败的写操作。不让他看状态，他只会报"系统坏了" |
| 状态兜底成 `not_activated` + `readOnly: true`，不是 `active` + 可写 | 认不出来的状态当成正常，等于把一个我们还不认识的授权问题渲染成一切正常 |
| 顶部横幅**不可关闭** | 状态还在，关掉只是让人看不见它。关掉之后再撞上写操作失败，就完全没线索了 |

### 2.7.4 字典类下拉一律从接口取，禁止前端写死

**已经栽过一次**：角色下拉在前端写了一份常量，于是界面上给出 `cmdb_operator`
和 `cmdb_security` 两个选项 —— **数据库里根本没有这两个角色**；
而真实存在的 `cmdb_asset`、`cmdb_cluster` 一个都选不到。
同一份清单当时散在三个页面里（用户管理、SSO 的 JIT 角色、MCP 令牌），
改一处漏两处几乎是必然。

两种后果都不好查：

- 后端有校验：报"角色不存在"，而用户明明是从下拉里选的，只会以为系统坏了
- 后端没校验：写进去一个不存在的角色代号，那个账号从此每个页面 403，
  而用户列表里它看着一切正常

适用范围是所有**真相在数据库里**的清单：角色、环境、项目、CI 类型、
通知渠道、数据源类型。判据一句话：**这份清单能不能被别人改？能，就不许写死。**

⚠️ 取不到时返回**空下拉**，不要回退到一份写死的兜底清单。
回退会让用户在接口挂掉时看到一个"看起来正常"的下拉，选完保存失败，
而失败原因和下拉里那几项毫无关系。

### 3.3.1 幂等键要用上游对象自己的身份

采集类表的唯一键，优先用**上游对象自己的唯一标识**（k8s 的 Event 名、
云资源的 self_link），而不是"业务字段的组合"。

实测教训：k8s 事件用 `(对象, reason, 首次时间)` 当键，会把同一个 Pod 的
`ErrImagePull` 和 `ImagePullBackOff` 合并成一行 —— 两者 reason 都是 `Failed`、
首次时间相同。而丢掉的那条恰恰说明了失败是怎么演进的。

⚠️ 反过来也要防：**没有幂等键**的话，每轮采集都插一行，
同一个 FailedScheduling 一天出现 288 条，界面上看起来像"炸了 288 次"。

### 3.4.0 聚合页只汇总已有判据，不新造判据

首页/概览类页面必须**复用各列表页那份判据**，链接直达带好筛选条件的列表。
首页说 3 条异常、点进去看到 5 条，是最快毁掉信任的方式。判据要改，改的是列表页那份。

⚠️ 聚合页里**每一项统计都要能表达"没统计出来"**（用指针 / null），并把它排在最前。
统计失败显示成 0，等于在首页上给一个我们根本没看过的维度发合格证 ——
这一条在本地实测时立刻抓到了一个真 bug（跨表排序规则冲突让两条 LB 统计恒失败）。

⚠️ 空态措辞要限定范围：说「当前没有需要关注的事」而不是「一切正常」，
并注明"这是在已接入的数据源范围内"。一个采集全断的环境本来也会显示"没有异常"。

### 3.4.1 「暴露面」的判据不能只看类型或只看有没有 IP

k8s 把**内网 LB 的 VIP** 也写进 `status.loadBalancer.ingress`（我们的 `external_ip` 列）。
所以：

- `type == "LoadBalancer"` **不等于**对外暴露 —— 内网 LB 也是这个类型
- `external_ip != ""` 也**不等于**对外暴露 —— 那个 IP 可能是私网的

正确判据是「有 Ingress 主机名 **或** 外部 IP 是公网地址」，并把私网 VIP 单独标成
"内网 LB"。不这么分的话，暴露面清单里会塞满内网服务 ——
**而误报多了，真正暴露在公网的那几个就没人看了**。

⚠️ IP 解析失败时按**非公网**处理：反过来会把一个读不懂的值当成公网地址塞进安全清单。
宁可漏一条待人工核对，也不要往安全清单里加噪声。

⚠️ 「拿不到外部 IP」是**第三种**状态，不是"没暴露"：配额用尽、子网没空闲 IP 时
LoadBalancer 会一直挂着，而 Service 本身看起来一切正常。

### 3.4.3 页面级的「没采到」必须区别于「确实没有」

字段级用 `NoValue`（§2.2），**页面级用 `NotIngested`**。两者解决的是同一类问题
的不同粒度：`EmptyState` 说"这里确实没有东西"，`NotIngested` 说
"**我们没能拿到数据**，所以不知道有没有东西"。

判据很硬：**这类对象有没有可能真的一条都没有？**

| 页面 | 空列表的真实含义 | 用什么 |
|---|---|---|
| 防火墙规则 | 任何 VPC 都有默认规则 → 只可能是没采到 | `NotIngested` |
| GCP IAM 授权 | 任何项目都至少一条绑定 → 只可能是没采到 | `NotIngested` |
| CDN 站点 | 可能真没用 CDN，但更可能是没接凭据 | `NotIngested` |
| 事件中心 | 真的可以很安静 | `EmptyState` |

后端已经在几个接口上返回 `empty_hint` / `not_comparable` 说明"为什么是空的"——
**前端必须原样显示这句话，不要自己另写一句**。只有后端知道到底是没配凭据
还是配了但缺 `roles/iam.securityReviewer`，前端拿到的只是一个空数组，
在这里编原因，编出来的多半是错的，而错的原因比没有原因更浪费时间。

最贵的一次形态是权限审计页：采集挂掉时渲染成普通空态，
界面上写着"没有发现风险授权"——它让人**放心**，于是不再去查。

同理，**"比对没成立"要独立于"比对通过"**：DNS 一致性在一方没数据时
返回 `not_comparable`，此时「0 个冲突」不是结论。把它显示成"两边一致"
和上面是同一个错误。

### 3.4.2 凭据类字段：列表接口一律不返回

证书私钥、云账号 AK/SK、kubeconfig、webhook URL —— 这类字段**不进任何列表响应**，
详情接口也只在有明确用途时按需返回并记审计。

⚠️ 查询要写**显式列清单，不要 `SELECT *`**：加字段时必须有人手写一行，
顺手加进表的敏感列不会自己跑到响应里。上一代在证书接口上出过 P0，
私钥被发给了所有有读权限的人 —— 它不报错、不影响功能，
只是安静地躺在每个人的 devtools 里，直到有人注意到。

⚠️ 连**样例数据**里也不要放真的私钥：种子会被人随手 `SELECT *` 打印出来。

⚠️ **这条不只管"列表接口"，配置/设置接口一样管。**
实测 ops-cmdb v0.82.0：`GET /api/settings` 把飞书 Webhook **全文返回**，
界面还用 `<input type="text">` 明文显示（85 字符，无掩码）。
拿到它的任何人都能以机器人身份向该群发消息（伪造告警、伪造到期通知）。

**而同一个产品的另外两处做对了**，可以直接照抄：

```jsonc
// 数据源列表：只回枚举，从不回值
{ "has_credential": true, "credential": "configured" }   // 或 "none"
// MCP 令牌：只回前 8 位
{ "hint": "2ad59d84" }
// SSO Client Secret：input type=password + 文案「只写入，任何接口都不会把它读出来」
```

**统一写法**：凭据类字段一律 `has_x: bool` +（可选）`x_hint: "前若干位"`，
写入用"留空表示不修改"语义。**同一套系统里出现两种标准，就等于按最松的那种泄露。**


### 3.4.6 「从多个候选里按规则选一个」时，必须把**选中的那个和为什么没选其它的**一起返回

数据源、接入点、费率、集群、凭据 —— 凡是运行时按规则挑一个候选的地方，
只返回结果不返回选择过程，**选错了就完全看不出来**。

⚠️ **本项目为此付出过最高代价的一次**：
infra-01 的 `environment` 配成了 DEV，于是查指标时匹配到 `dev-prometheus`
而不是 `infra-victoriametrics`，**返回 0 条**；
`resource_waste` 把它渲染成「用量 0%」，据此建议把 logstash
**从 18 核砍到 10 毫核、24GB 砍到 64Mi** —— 照做会当场 OOM。

整条链路上没有任何一处显示"我现在查的是哪个数据源"。

✅ **正确做法**（`data_freshness` 已经这么做了，照抄即可）：

```jsonc
"obs_stack": [
  { "type":"prometheus", "name":"infra-victoriametrics", "healthy":true,
    "selected": true,
    "selected_note": "本集群查 prometheus 时用的就是这条" },
  { "type":"prometheus", "name":"dev-prometheus", "healthy":true,
    "selected": false,
    "selected_note": "本集群不会用它（按环境/集群匹配后选中的是另一条）" }
]
```

**三条要求**：

1. **候选全列**，不是只给选中的那一个 —— 只给结果就无从判断规则对不对
2. **`selected` 是显式布尔**，不要让消费方从顺序或其它字段推断
3. **没选中的也要给理由**（`selected_note`）—— "为什么不是它"往往才是排查的入口

⚠️ 同类场景还有：费率表按「区域+机型族」回退到 `default` 档
（[OPSCMDB-031 P1-47](../docs/ops-issues/clusters/platform-ops-cmdb/OPSCMDB-031-full-verification-uat-dev.md)：
回退发生了、结果看着完全正常、但没有任何地方说它回退过）。
判据一样：**凡是"没精确匹配就退而求其次"的地方，退到哪一档必须显式返回。**

### 3.4.5 转发上游响应时不要再套一层 `data`

实测 ops-cmdb 资源使用率页整页不可用，根因就是这个：

```jsonc
// 后端把 Prometheus 原始信封整个塞进自己的 data
{ "ok": true, "query": "...", "data": {          // ← 我们的 data
    "status": "success",
    "data": { "resultType": "matrix",            // ← Prometheus 的 data
              "result": [ { "values": [ ...61 个点... ] } ] } } }
```

真实路径是 `data.data.result`，前端读 `data.result` → `undefined` →
判定为"无数据" → 界面显示「这个时间范围内没有数据点。**可能是对象名写错了**」。

**代价**：查询成功、61 个数据点、`seriesFetched: 225`，
界面却告诉用户是他自己名字填错了。图表、指标切换、时间范围、
四种对象类型**全部卡在这一个解析上没法用**。

**规则**：转发上游响应时**解包到我们自己的契约**，不要原样嵌套：

```jsonc
{ "ok": true, "query": "...", "result_type": "matrix", "series": [...] }
```

如果确实要保留原始信封（调试用），放在 `raw` 字段里，**不要占用 `data`**。

⚠️ 顺带：**错误文案不要替用户猜错误原因**。
「可能是对象名写错了」在这里是错的，而且把人推向了完全错误的排查方向。
拿不准原因时说"没有返回数据点"，然后把 query 和 `seriesFetched` 显示出来
——让人自己判断，比猜一个理由好。

### 3.5 迁移

| 规则 | 为什么 |
|---|---|
| **所有 schema 变更走迁移文件**，绝不手动改库 | 手改的结果是生产和迁移记录对不上，下次部署 pod 崩 |
| 迁移号连续递增，不复用 | |
| `ops/.gitignore` 有 `!**/migrations/*.sql` 反否定 | 仓库根的 `*.sql` 会吞掉迁移文件，镜像靠 go:embed 能跑但 git 里没有 |
| **注册了 cron 处理函数，还要在 `scheduled_tasks` 里登记** | 只做一半的后果很隐蔽：代码看着有、界面找不到、不报错，只是那份数据永远不更新 |
| 定时任务的频率要匹配数据变化速度 | 云资源变化慢（每天一次够），磁盘写满是快速变化的（每天一次的话从 70% 到 100% 全程无感知） |
| **唯一索引下"这一项不适用"必须是 `NULL`，不能是空串或 0** | 见下 |

#### 3.5.2 软删的表，唯一索引必须带 `del_key`

有 `deleted_at` 的表，唯一索引一律写成 `UNIQUE (…业务键…, del_key)`，
其中 `del_key BIGINT NOT NULL DEFAULT 0`：活行恒为 0，软删时**同时**置为自己的 `id`。

**两个方向都会出事，而且症状相反：**

| 写法 | 症状 |
|---|---|
| 唯一索引里带 `deleted_at` | 索引形同虚设。MySQL 不约束 NULL，而活行的 `deleted_at` 全是 NULL，于是**活行之间互不冲突**，重复数据照插不误。隐蔽在于 `SHOW CREATE TABLE` 看着完全正常 |
| 唯一索引里什么都不带 | 删得掉、建不回。软删的行还占着那个标识，再建同名的报「已存在」——而人会去列表里找那个"已存在"的东西，找不到 |

⚠️ 配套要求：**每一处软删的 SQL 都要写 `SET deleted_at = NOW(), del_key = id`**。
漏写 `del_key` 的话这个索引等于没做。已经漏过两处（删网关路由、删分组时连带的授权规则），
表现都是"删完之后同一个东西再也配不回来"。

#### 3.5.1 唯一索引 + 非空默认值 = 第二行就插不进去

给 `users` 加 `idp_subject`（SSO 的用户标识）时写成了
`VARCHAR(255) NOT NULL DEFAULT ''` 再加唯一索引。所有没接 SSO 的账号
`idp_subject` 都是 `''`，于是唯一索引在**第二个本地账号**上就炸了：

```
Error 1062: Duplicate entry '' for key 'users.uniq_idp_subject'
```

两个要命的地方：

1. **报错指不回真正的原因。** 那句话里没有一个字提到 SSO。真在生产上撞到，
   现象是"新建用户失败"，而排查方向会全跑偏。
2. **它可能很久之后才发作。** 只有一个用户的环境（刚装完、演示库）完全正常，
   等客户建第二个账号时才炸——那时候没人会想到是几个月前那次迁移。

MySQL 的唯一索引允许任意多个 `NULL`，这正是"不适用"该有的表示法。
空串和 0 都是**具体的值**，它们的意思是"这一项就是空串/就是零"，
和"这一项没有"是两回事——与 §3.3 的三态是同一条道理，只是这次由数据库来执行。

同类陷阱：软删除表上的唯一索引带 `deleted_at`，而 `deleted_at` 默认 `NULL` 时
索引不生效（`NULL != NULL`），删掉再建同名记录会撞；用 `0` 当"未删除"才有效。
方向正好相反——**先想清楚这个索引要拦的是什么**，再决定用 `NULL` 还是哨兵值。

### 3.5.2 后台任务必须逐租户跑，且"全挂"不能报成"没数据"

多租户下，定时任务不能有一个「能看所有租户」的作用域。正确写法是
`store.ForEachTenant`：先列启用中的租户，再**逐个**构造作用域，
每一轮只能碰一个租户的数据 —— 越权在 Scoped 层被挡下，而不是靠人记得加条件。

这条是四个任务同时挂掉之后补上的：证书自动续期、磁盘水位巡检、
DNS 同步、主机同步，全都写成了

```go
st.Platform("host_sync").Query(`SELECT tenant_id, id FROM cloud_account_projects`)
```

`Platform()` 只放行平台级白名单表，而这些都是租户表 —— **查询从来没成功过一次**。
而因为 `scheduled_tasks.last_ok` 默认值是 1，界面上这四个任务一直显示「正常」。

三条配套的硬规则：

| 规则 | 为什么 |
|---|---|
| 单个租户失败**不中断**其余租户 | 一个租户凭据过期不该让所有租户的同步都停摆 |
| **所有租户都失败 = 任务失败** | 否则会变成"检查了 0 个集群：无超阈值磁盘"—— 报的是成功，读起来还像好消息 |
| 部分失败要**进摘要**，不能只写日志 | 界面上一句干净的"成功"，而某个租户的数据其实一直没更新 |

⚠️ 第二条是修这个 bug 时**我自己踩的**：第一版把 `ForEachTenant` 的失败计数丢掉了，
于是任务从"响亮地失败"变成了"静默地成功"。**把一个响亮的失败改成静默的成功，
是比不修更糟的修法。**

⚠️ `partial`（部分成功）的前提是**至少一项成功了**。
0 成功 / N 失败被记成 partial，界面上就是一个绿色的「正常」。
任务自己知道成功了几项，调度器不知道 —— 所以"一项都没成"必须由任务返回 `ok=false`。

`internal/store/platform_misuse_test.go` 会静态扫描 `Platform()` 的用法。
它扫代码不扫注释：文档里演示反面写法是有价值的，扫注释会逼人把教训删掉。

### 3.5.2.1 删除字典项之前必须数"还有谁在用"

字典项（环境、项目、类型）被删掉之后，**引用它的资产不会跟着变** ——
`hosts.project` 里那个字符串还在，只是下拉里再也没有这一项。
表现是：那批资产从筛选视图里消失，列表里却还在，没有任何报错。
想找回来只能靠人记得原来叫什么。

所以删除前要数引用，**并把数量报给用户**：光说"不能删"没用，
他要知道接下来得改多少条。

⚠️ 数不出来时**不放行**：查询失败的时候"没有引用"这个结论并不成立。

⚠️ **列名相同不等于语义相同，必须查数据确认**。
`projects` 这张字典存的是业务项目（"游戏中台"、"支付"），
而 `hosts.project` / `cis.project` 存的是**云项目 ID**（g32-prod、infra-01）——
完全是另一套东西。第一版把它们都算成引用，结果会是
"删一个从没被用过的业务项目，被告知还有 9 条资产在用"，而那 9 条毫无关系。

⚠️ 同理，**别的字典的字段名不能照抄**：`lifecycle_statuses` 用的是
`scope` + `label`，不是 `code` + `name`。照抄会渲染出一排空标签 ——
不报错，就是空的。

### 3.5.3 文档里的示例代码也会错，也需要被验证

上面那四个任务不是各自写错的，是**照着 `ForJob` 的文档注释抄的** ——
那段注释里的"正确示例"本身用的就是 `Platform()` 查租户表。
一个错误示例批量生产了四个坏实现。

所以：**示例代码要么来自真实跑通的代码，要么就明确标注是反面例子。**
文档里的代码不会被编译、不会被测试，但会被复制。

### 3.6 多副本

服务默认按多副本部署，下面每条都必须成立：

| 项 | 要求 |
|---|---|
| 定时任务 | 必须走 `leases` 表选主，否则 N 个副本重复采集 |
| 数据库迁移 | 要加锁，多副本同时启动会抢跑 |
| License 状态 | 定期从 DB 热加载（30–60s），**不能只在启动时读**，否则激活后要重启全部副本 |
| 安装指纹 | **必须来自数据库**，绝不取宿主机 MAC/hostname |
| 会话 | JWT 无状态或集中存储，本地内存 session 在多副本下必然掉登录 |
| 文件导出 | 不能落本地盘，下次请求可能到别的副本 |
| 写操作 | 幂等或带幂等键，多副本 + 重试会放大重复提交 |

**安装指纹为什么不能绑主机**：每个 Pod 的宿主机标识都不同，用宿主机派生会让绑定安装的 license 在部分副本上校验失败，表现为「重启后偶发提示未授权」——只在部分请求上出现，是最难排查的一类故障。绑数据库等价于"绑这套部署"，对客户也更合理，Pod 本来就会漂移。

### 3.7 非幂等写操作（扣费、签发、外部写入）

- 失败 **≠** 没生效。响应丢了但对方可能已经受理。
- 结果必须是**三态**，不能压成 bool：`已成功` / `待核对`（响应丢了，回查确认已生效）/ `失败`（回查确认没生效）。
- 重试的门槛要高：必须**回查确认没生效** + 错误是瞬时类。"查不出来"一律不重试。
- 每一笔都要落台账并记审计。

### 3.8 `RowsAffected` 不能当「找到没有」用

MySQL 的 `RowsAffected` 数的是**真正被改动的行**，不是匹配到的行。
所以这个写法是错的：

```go
res, _ := q.Exec(`UPDATE apps SET name = ? WHERE id = ?`, name, id)
if n, _ := res.RowsAffected(); n == 0 {
    return sql.ErrNoRows   // ✗ 打开编辑框什么都不改直接保存，就会走到这里
}
```

**实测撞到过**：点「编辑」→ 不改任何字段 → 「保存」→ 界面报「不存在」，
而那个应用就在下面的列表里。人第一反应是数据丢了。

正确做法是**在 UPDATE 之前显式查一次存在性**。

⚠️ 不要图省事在 DSN 上开 `CLIENT_FOUND_ROWS`：那会改变**所有**
`RowsAffected` 的语义。有些地方恰恰是靠"改动了才算成功"来判并发抢占的
（审批只能从 pending 改走、一次性口令只能用一次、授权码只能换一次 token），
全局改掉会让它们在状态不对时也返回成功 —— 那是安全问题，不是体验问题。

判据：`WHERE` 里带了状态条件、且 `SET` 必然改变某一列（`deleted_at = NOW()`、
`used_at = NOW()`、`status` 换值）的，用 `RowsAffected` 判抢占是对的；
其余一律先查存在性。

### 3.9 审计 detail 里放什么类型都不该影响哈希链

审计链对 detail 做规范化之后再哈希。规范化函数必须**先把任意值降解成
`map[string]any` / `[]any` / 标量**再排序输出。

**为什么**：写入侧拿到的可能是一个 Go 结构体（`json.Marshal` 按**字段声明顺序**输出），
校验侧拿到的是从 MySQL JSON 列解析回来的 map（按字典序输出）——
两边字节不同，于是那条记录被报成「内容被改过」，而它谁也没动过。

实测撞过两次，同一个陷阱的两个入口：一次是 MySQL JSON 列重排键，
一次是 detail 里放了结构体。所以修在规范化函数里，而不是要求每个调用方
记得传 map —— 让调用方传什么类型都不影响结论。

⚠️ 一个天天喊狼来了的防篡改机制比没有还糟：人会直接不看它，
于是真出事的那次也不会有人看。

### 3.6 面向 AI 的接口：失败必须让 AI 也看得出是失败

三态约定（§3.4）针对的是人看的界面。同一套原则对 MCP / AI 接口成立，
而且要求**更严**——AI 不会追问，它会把手上的东西直接当结论转述给人。

#### 3.6.1 桥接内部接口时必须看状态码

把 MCP 工具实现成"转发到内部 REST 接口"是对的（工具与接口永远一致），
但转发层**必须检查 HTTP 状态码**：

```go
// ✗ 错：403「没有操作权限」的 body 被当成成功结果交给 AI
b, _ := io.ReadAll(resp.Body)
return string(b), nil

// ✓ 对
if resp.StatusCode >= 400 {
    return "", fmt.Errorf("内部接口 %s 返回 HTTP %d: %s", path, resp.StatusCode, body)
}
```

错的那版，AI 收到的是一次 `isError` 未置位的**正常返回**，
内容恰好是个 JSON 错误对象。它多半读成"查到了，是空的"，
然后向人转述"该项没有数据"——一次权限问题被讲成了一个事实结论。

失败必须落到 MCP 的 `isError: true` 上，那是协议里表达失败的唯一位置。

#### 3.6.2 工具清单要按调用方实际能调的过滤，不能"列出来再拒"

`tools/list` 必须按**这个令牌真正能调的**返回。过滤有几条轴（授权分档、
令牌角色……），**每一条都要应用**——漏掉任何一条，效果就是清单里有、调用时被拒。

对人来说"点了才发现没权限"只是体验差；对 AI 是行为错误：
它按清单规划排查路径，撞上"没有操作权限"后无从判断是权限问题还是系统故障，
通常的反应是重试，或者向人报"系统异常"。**看不见的工具它不会去想。**

⚠️ 这条最容易只落实一半：先有了分档过滤，后加角色时忘了同一个理由也适用。
过滤判据必须与调用时的鉴权判据**同源**（直接复用路由权限表，
不要另建一张"工具→权限"的映射——两张表迟早分叉）。

判不出某个工具需要什么权限时，按不可调处理**并告警**：
调用时它一样会被拒，但那是配置漏了，得有人知道。

#### 3.6.3 数据可不可信要能被问出来

AI 拿不准的时候需要一个地方确认"我看到的这份数据是什么时候采的"。
提供一个新鲜度工具，并且明确给出结论而不只是时间戳：

```json
{"cluster_name":"...","overall":"never","trustworthy":false,
 "advice":"该集群从未成功采集过，CMDB 里没有它的数据，不要基于此下任何结论"}
```

只给 `last_sync` 时间戳不够——那要求 AI 自己判断多久算旧，它会猜。

## 4. 部署

### 4.1 Helm：一个产品一个 chart，前后端同一个

| 规则 | 为什么 |
|---|---|
| 前后端同 chart | 后端地址由 chart 推导（`{{ include "x.fullname" . }}-backend`），不用人填。地址靠手工同步是反复出问题的根源 |
| `helm rollback` 一次回到完整上一版 | 分两个 chart 会出现"前端升了后端没升" |
| 独立升级用 `--set frontend.image.tag=` | checksum 只挂在各自的 Deployment 上，不会互相触发 |

**本地 / 生产两套 values**：

| | 本地 | 生产 |
|---|---|---|
| Service | NodePort（固定端口） | **ClusterIP** |
| 入口 | k8s-proxy 转发 | Ingress + 域名 + TLS |
| 反亲和 | `preferred` | `required` |

**生产绝不开 NodePort**：它在每个节点上开一个端口，等于绕过 Ingress 的鉴权与 WAF，是最容易被忘掉的公网暴露面。

**本地端口要在 k8s-proxy 的三处同步**：`nginx.conf` 加 server 块 + `docker-compose.yml` 加 ports + `README.md` 端口表。改 ports 后必须 `docker compose up -d` 重建容器，光 reload 不生效。

**禁止临时 `kubectl port-forward`**：端口随机会跟别人占用的撞，请求打到别的服务上。

### 4.5 容器一律非 root

容器里的 root 就是宿主机的 root。一旦有逃逸或挂载配置失误，
root 进程能碰的东西比普通账号多一个量级 —— 这是等保 / SOC2 必查项。

| 规则 | 为什么 |
|---|---|
| **Dockerfile 的 `USER` 必须是数字** | `runAsNonRoot: true` 时 kubelet 要在启动前判断镜像用户是不是 root。写成 `USER nginx` 它查不到 uid，直接报 `container has runAsNonRoot and image has non-numeric user`，Pod 起不来 |
| **uid 只在 Dockerfile 定义一次**，chart 只写 `runAsNonRoot: true`，不写 `runAsUser` | 两处各写一个数必然分叉。实际撞到过：Dockerfile 写 10001、chart 写 65532，而 65532 在镜像的 `/etc/passwd` 里根本不存在。k8s 里 chart 赢、`docker run` 跑 10001 —— 同一个镜像两种身份，且**两种都能跑**，所以没人发现 |
| 前端用 `nginxinc/nginx-unprivileged` | 官方 nginx 镜像以 root 起，与 runAsNonRoot 冲突会 CrashLoop。这个镜像默认监听 8080，非特权端口，不需要 `NET_BIND_SERVICE` |
| 配套 `readOnlyRootFilesystem: true` | 要写的路径挂 emptyDir。只改 uid 不锁根文件系统，逃逸后照样能改镜像里的东西 |
| `allowPrivilegeEscalation: false` + `capabilities: drop ["ALL"]` | 防止通过 setuid 二进制提回 root |

⚠️ **验证别看 Dockerfile 猜，进容器问它自己**：

```bash
kubectl exec -n <ns> deploy/<name> -- id -u    # 输出 0 就是没做到
```


### 4.2 探针：三种职责不同，参数不能共用

| 探针 | 职责 | 阈值 |
|---|---|---|
| `startupProbe` | 保护慢启动的容器不被 liveness 杀掉 | 宽松，迁移可能跑很久 |
| `readinessProbe` | 决定是否接流量，失败就摘出 Endpoints | 灵敏 |
| `livenessProbe` | 只在真死了才重启 | **必须比 readiness 宽松** |

用专门的 `/healthz` 端点，不要拿 `/` 做探针（会返回整个 index.html，探针流量白占带宽，日志被刷满）。

### 4.3 静态资源缓存

| 路径 | 缓存 |
|---|---|
| `/assets/*`（带内容哈希） | `1y, immutable` |
| `/index.html` | **`no-store`** |
| `/version.json` | **`no-store`** |

**为什么 index.html 绝不能缓存**：发新版后用户手里是旧 index.html，它引用的 assets 哈希文件已经不存在了 → **整页白屏**，而且只发生在老用户身上，新访客一切正常，极难复现。

### 4.4 其它部署细节

| 项 | 说明 |
|---|---|
| 单副本**不创建 PDB** | 单副本 + `minAvailable:1` 会让节点排空永远卡住——驱逐这唯一的 Pod 违反 PDB，不驱逐节点就下不掉 |
| `readOnlyRootFilesystem` 要挂 `/tmp` emptyDir | nginx 要写临时目录，否则 CrashLoop |
| `preStop: sleep 5` | 让 Endpoints 摘除生效，避免滚动更新时零星 502 |
| `maxUnavailable: 0` | 先起新的再停旧的，滚动期间容量不下降 |
| ConfigMap 变更要挂 `checksum/config` 注解 | ConfigMap 更新本身不会重启 Pod，少了它改完配置以为生效了其实没有 |
| 容器内探测用 `127.0.0.1` 不用 `localhost` | `localhost` 同时解析 `127.0.0.1` 和 `::1`，客户端先试 IPv6 而 nginx 只绑 IPv4，报 Connection refused 看着像服务挂了 |
| 静态服务不设 CPU limit | nginx 的 CPU 是突发型的，设了会在尖峰被限流，表现为偶发的请求变慢 |

### 4.7 生产 values 必须显式写 resources；HPA 阈值必须够得着

`resources` 写在 `values.yaml`、`values-prod.yaml` 不覆盖，helm 渲染是对的 ——
但**上线前人读的是 `values-prod.yaml`**，那里看不到生产给了多少资源。
「生产给了多少」这个问题要翻到另一个文件、还要知道它会被继承才答得出来。

所以生产 values 里 requests/limits 一律显式写全，哪怕和默认值一模一样。
守卫：`tooling/scripts/check-prod-resources.mjs`。

⚠️ **request 不能贴着实测值。** 它是调度器算节点余量的依据，
贴着实际用量会导致超卖：节点看起来还有空间、其实已经满了，
然后在流量高峰一起被驱逐。ops-cmdb 前端原来 request 32Mi、
同类前端生产实测 26.8Mi，只有 16% 余量。

⚠️ **反过来也不能虚高。** request 是预留，占着就是花钱，哪怕一直没用到。
四集群体检里最大的一笔浪费就是「CPU request 虚高 4.5 倍」。

### 4.6.1 镜像仓库与拉取凭据放 `global`，组件里只写镜像名

```yaml
global:
  imageRegistry: harbor.example.com/ops   # 前缀，不含镜像名
  imagePullSecrets: []                    # 所有组件共用
frontend:
  image:
    repository: ops-cmdb-frontend         # 只写名字
```

⚠️ 各组件写完整地址时，换仓库要改多处，而**只改一处不会报错**：
改了的正常拉、没改的还在拉旧仓库，两个镜像都能起来，只是版本对不上 ——
表现为"前端升了后端没升"这类最难复现的错配。

客户换仓库只要一行：`--set global.imageRegistry=registry.customer.com/ops`。
守卫：`check-prod-resources.mjs` 会拒绝 `repository` 里出现 `/` 或 `:`。

### 4.6.2 前后端逐字相同的配置只留一份

`securityContext` 曾在前后端各写一份、内容完全一致。
两份一模一样的配置，改的时候必然只改一处，而分叉之后两边都能跑 ——
没人会发现，直到某个按属主授权的地方失败，报错却只说 permission denied。

抽进 `_helpers.tpl`。⚠️ 不要为了"以后可能不一样"提前拆两份；
真出现差异时再拆，并写清楚为什么不同。

`resources` / `autoscaling` / `service` 这些**本来就该不同**的不算重复，保留各自一份。

#### 4.7.0 requests 与 limits：cpu、内存四个值都要写

四个值一个都不能省，各自防的是不同的事：

| | cpu | memory |
|---|---|---|
| **request** | 调度依据 **+ HPA 算利用率的分母** | 同左 |
| **limit** | 超了被**限流**（cfs throttling） | 超了被 **OOMKill** |

⚠️ 没有 limit 的容器可以吃满整个节点，把同节点其它服务一起拖垮。
⚠️ CPU limit 是双刃剑：限流表现为**偶发的请求变慢**，而且监控上看不出是被限流的。
所以给到 request 的 4~10 倍（突发型负载取大值），而不是贴着 request 给。

#### 4.7.1 开 HPA 前先算一遍扩容阈值

扩容阈值 = `cpu request × targetCPUUtilizationPercentage`。

ops-cmdb 前端踩过：request `10m` × 70% = 阈值 `7m`，
而同类前端生产实测 CPU 是 `0.037m` —— **差 190 倍，这个 HPA 数学上不可能触发**。

它不提供任何保护，只提供「我们配了自动扩容」的错觉。
而**错觉比没有更危险**：真出容量问题时，没人会去查一个"已经配了 HPA"的服务。

规则：开 HPA 就必须给一个像样的 cpu request（≥50m）。

#### 4.7.2 HPA 必须同时挂 CPU 和内存两个指标

只挂 CPU 对静态服务等于没有保护 —— nginx 几乎不吃 CPU，先撑不住的一定是内存。

语义要知道：**任一指标超阈值就扩容**（取各指标算出的副本数的最大值），
而缩容要**全部**低于阈值才发生。这是 HPA 的既定行为，不是配置项。

⚠️ **内存指标基本是单向的。** Go 运行时和 nginx 都不怎么把内存还给 OS，
RSS 涨上去很难落回来，所以内存触发的扩容多半**不会自己缩回去**。
这不是配错了，是内存这个指标的性质 —— 把它当"别再涨"的保护，
不要指望它像 CPU 那样自动收敛。

#### 4.7.3 本地也要开 HPA，且必须装 metrics-server

形态和生产一致才验得出问题（副本数变化时的会话、粘性、leader 选举）。

⚠️ **docker-desktop 默认没有 metrics-server**。没装时 HPA 显示
`<unknown>/70%` 并且**永远不扩容**，而 `kubectl get hpa` 不会报任何错 ——
和配好的样子几乎一样。装法（kubelet 证书自签，必须加 `--kubelet-insecure-tls`）：

```bash
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl -n kube-system patch deploy metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
```

⚠️ 本地 `maxReplicas` 要比生产小（单节点扩到 8 个只是把同一台机器的资源
切得更碎，验不出东西还挤掉别的服务）。

⚠️ 开了 HPA 之后 `replicaCount` 只在**第一次创建**时生效，之后由 HPA 接管。

#### 4.7.3.1 开了 HPA 就不能再写死 `replicas`

Deployment 里同时有 `replicas` 和 HPA 时，**每次 `helm upgrade` 都会把副本数
按回 `replicaCount`**，砍掉 HPA 扩出来的实例，HPA 随后再扩回去。

表现是「每次发布之后容量掉一截然后慢慢恢复」，而发布日志、HPA 事件、
Deployment 状态**全都正常** —— 没有任何一处会报错。

```yaml
{{- if not .Values.backend.autoscaling.enabled }}
replicas: {{ .Values.backend.replicaCount }}
{{- end }}
```

⚠️ 这个坑在 ops-cmdb 后端上真实存在过：前端做了这个判断，后端没有。
守卫：`check-prod-resources.mjs`。

#### 4.7.3.2 `revisionHistoryLimit` 设成 3

默认是 10：每次发布留一个 ReplicaSet，频繁发布的服务会在 etcd 里
堆一堆没人看的对象（DEV 集群 1.86 万对象里过半是这类垃圾）。
3 份足够回滚 —— 真要回到更早的版本，`helm rollback` 看的是 release 历史，
不是 ReplicaSet。

#### 4.7.4 扩容之后必须复验 leader 选举

副本数由 HPA 动态变化时，"定时任务只跑一次"这件事更容易出问题。
扩容后查一次租约持有者：

```bash
kubectl -n <ns> logs -l app.kubernetes.io/component=backend --tail=200 | grep leader_change
```

必须**恰好一个** `"leader":true`。每个副本都跑定时任务时，
域名续费是非幂等写 —— 4 副本等于扣 4 次钱。

## 5. 构建与版本

### 5.1 构建期防线

`pnpm build` 会先把它们跑一遍再编译，任一失败不出产物。
**它们的共同点是拦"不报错但做错"的问题**。

| 脚本 | 拦什么 |
|---|---|
| `check-hardcoded-colors.mjs` | 组件里写死颜色，白标换色后那一处不跟着变 |
| `check-i18n.mjs` | 漏翻、占位符对不上、复数形式缺失（管**两种语言之间**对不对齐） |
| `check-i18n-usage.mjs` | 代码引用的 key 语言包里没有（管**代码与语言包之间**对不对得上）。i18next 取不到 key 时不报错，它把 key 本身当文案渲染 —— 界面上就出现一个写着 `write.create` 的按钮，功能全对、只有那几个字是错的。实测靠截图才发现 |
| `check-error-keys.mjs` | 后端错误码在前端语言包里没有文案，用户会看到生的 key |
| `check-license-keys.mjs` | 授权状态没有对应文案。**授权状态是最晚才出现的一类界面**（`lapsed` 要欠费满 30 天），漏了不会有人发现，直到它出现在客户屏幕上 |
| `check-perm-codes.mjs` | 前端菜单的 `perm` 与后端 `perm.go` 不同名。写错不报错，只是该菜单对所有非管理员静默消失——而管理员自己看不出来 |
| `check-shared-capability-wired.mjs` | 共享包里**面向用户的能力**没有产品入口。见下面 5.1.1 |

⚠️ 写这类检查器时，**正则不要依赖字段顺序**（"key 后面紧跟 perm"）：
格式化工具一重排就抽不全，而脚本照样打印 ✓。
第一版就是这么漏掉 6 个菜单还报"全部有效"的 —— **防线自己失效比没有防线更危险**，
因为它给了一个已被覆盖的错觉。所以检查器要能对自己的覆盖率做断言
（比如"抽到的 perm 数必须等于菜单项数"，对不上就报错）。

⚠️ 检查器**必须认 CLDR 复数后缀**：`t('certs:total', {count})` 在语言包里存的是
`total_one` / `total_other`，没有 `total` 这个 key。不认这条的话，
check-i18n-usage 会把几十个完全正确的复数 key 报成缺失 ——
而一个天天误报的检查等于没有检查，它只会被人加个 `--skip` 绕过去。

⚠️ 新写一道防线，**要反向验证它真的会失败**：故意引一个不存在的 key，
确认脚本非零退出。只看到 ✓ 不能说明它在工作 —— 见上面那条"防线自己失效"。

**新增防线的判据**：这个问题会不会"不报错、看起来正常、只有用户先撞见"。会，就值得加一道。

### 5.1.1 「有能力、没入口」有两层，守卫要分别覆盖

这是本项目撞得最多的一类缺陷，而它有**两个不同的层**：

| 层 | 症状 | 守卫 |
|---|---|---|
| 后端接口没有前端入口 | 接口能跑、无人调用 | `check-read-coverage` / `check-write-coverage` |
| **共享包的能力没有产品入口** | 组件写好了、产品不引用 | `check-shared-capability-wired` |

第二层是 OPSVER-032 才补上的。当时的情况是：

> `@ops/ui` 里 ThemeToggle / LocaleToggle / PreferencesMenu 三个组件早就写好了，
> `@ops/design` 的主题机制、`@ops/i18n` 的两份语言包（各 554 条、一条不缺）也全是好的。
> **缺的只有那个开关本身。** ops-sso 接了，ops-version 没接，谁都没发现 ——
> 直到用户问「怎么没有看到切换白天黑夜的，切换中英文的也没看到」。

🔴 两层是同一个形状，但**第一层的守卫查不到第二层** —— 它只扫后端路由表。
加共享能力时要顺手问一句：这个能力**每个产品都该有**吗？该有就登记进
`check-shared-capability-wired.mjs` 的 `CAPABILITIES`。

⚠️ 登记的判据是「**每个**产品都该有」。只有一两个产品需要的东西不属于这里 ——
一道总在报错、大家习惯性忽略的守卫，比没有守卫更糟。

⚠️ 它只查「有没有引用」，不查「渲染到哪儿了」。引用了却没挂上去的情况
守卫看不出来 —— 那一层只能靠验收时真的去点。

### 5.2 版本号

语义化版本，`v` 前缀，预发布只允许 `alpha` / `beta` / `rc`。详见 [VERSIONING.md](./VERSIONING.md)。

- `v0.x.y` 阶段不承诺兼容性；发 `v1.0.0` 意味着从此承诺。
- **前后端共用一个版本号**（同 chart、一起发布回滚）。
- **预发布版本禁止推对外仓库**（构建脚本会拦）：`-rc.1` 一旦进了对外仓库，就没法阻止别人拿它当正式版部署生产。
- **不用 `latest` 标签**：出问题时没人说得清当时跑的是哪份代码。

### 5.3 镜像构建

**只能用 `tooling/scripts/build-image.sh`，不要手工 `docker build`。**

**为什么**：漏传 `--build-arg VERSION` 会静默落成 `dev`，上一代四个前端全踩过，线上排障时完全看不出前端是哪一版。脚本把版本注入收口，并在构建结束时打印实际值。

其它必知：

- `.dockerignore` **必须排除 `node_modules`**，否则 `COPY . .` 会把宿主机依赖树盖到容器里已装好的那份上，pnpm 在非 TTY 下会直接报错中止。
- Node 25+ 官方镜像**不再自带 corepack**，用 `npm i -g pnpm@<版本>`，版本要和 `packageManager` 字段一致。
- 推对外仓库（marks26）**只推 `linux/amd64`**，需要 arm64 时显式加 `--multiarch`。
  🔴 这里曾经写的是"必须多架构（本地 arm64 / 生产 amd64）"，但那条理由不成立：
  **本地从来不从对外仓库拉镜像**——本地走 `localhost:8070` 的 Harbor（`--push`，原生 arm64），
  对外仓库只是送生产的通道，而生产 GKE 全是 amd64。传上去的 arm64 没有任何消费者。
  代价不是理论上的：后端 Go 二进制约 60MB 且每次改代码必变，双架构等于每次多传一份。
  实测一次后端推送 10 分钟，其中构建只占约 14 秒（其余全是缓存命中），全卡在 `pushing layers`。
- 推之前 Trivy 必须 0 漏洞（含 medium/low），前端另外要 `npm audit` 清零。
  ⚠️ 扫描要显式带 `--severity UNKNOWN,LOW,MEDIUM,HIGH,CRITICAL` —— **Trivy 默认不报 UNKNOWN**，
  不写的话"扫描通过"是一句没有内容的话。
  上游确实没有修复版本的，登记进 `SECURITY-WAIVERS.md` 再放行 ——
  **一条被忽略但没记录的漏洞，和一条不存在的漏洞长得一模一样**，
  下次扫出来还得重查一遍，而上游发了修复版也没人知道该回来看。
- **前后端的构建上下文都是 `ops/`**，不是各自那层目录：后端用 `replace` 指向同仓的
  `ops-kit/licensekit`，上下文给窄了报的是 `failed to compute cache key: "/xxx": not found`，
  完全看不出是上下文的问题。
- ⚠️ **别把构建命令管进 `tail` 再接 `&&`**：管道的退出码是 `tail` 的（恒 0），
  构建失败照样往下走，于是 helm 部署一个还没推上去的 tag —— ImagePullBackOff，
  而你以为镜像早就好了。要看尾部输出就分两条命令写。
- 二进制要支持 **`-version`**：确认镜像里到底是哪一版，不该要求先有一个能连通的数据库 ——
  启动失败的镜像恰恰是最需要确认版本的那个。

### 5.4 API 类型生成

后端 swag 注解 → Swagger 2.0 → OpenAPI 3.0 → TS 类型，`pnpm --filter @ops/api gen` 一条命令跑完。

- **只给正在做的接口加注解**，不追求全覆盖。接口还在改的时候先标注等于白标。
- `generated/` 下的文件**不要手改**：后端真改了字段时生成器会把改动冲掉，而在被冲掉之前，前端类型和后端实际返回已经对不上了，编译还是绿的。
- 生成时会删掉 swag 顺带产出的 `docs.go`——它 import `swaggo/swag`，会给后端凭空加运行时依赖，还多一处生产要记得关的暴露面。

---

### 5.4.1 新建文件/接口前先确认它不存在

两个真实教训，都发生在同一次改动里：

1. `cat > file` 会**无声覆盖**已有文件。新写 `registrars.go` 时覆盖掉了同名文件，
   而那里面有个被 6 处引用的 `LoadCredential`。编译时才发现 ——
   要是那函数恰好没人引用，就得等运行期才炸。用 Write 工具（它拒绝覆盖未读过的文件）。

2. **找接口在哪，要连 `internal/api/` 一起 grep**。我只扫了 `handlers/` 就断定
   "注册商后端不存在"，重写了一份，结果 gin 因路由重复注册直接 panic、Pod 起不来。
   这个仓库里接口分布在两处：旧的在 `handlers/`，迁移过的在 `internal/api/<域>/`。



### 5.5 有采集的功能，本地要真接一个数据源

事件、镜像仓库这类页面，光有表和接口是验不出来的：**幂等键选错、时间字段
取错、上游返回的形状与想象不同**，全都只有真连一次才会暴露。

本地能接的都接上（docker-desktop 集群、本地 Harbor）；
接不上的（GCP、生产告警）就把关键路径的日志打全，留给生产环境调试。

⚠️ SSO 这类"要跟别人的系统对接"的功能，本地起一个**真的**身份源来验
（Dex 一个容器就够）。自己写的 mock 只会返回我以为的东西，而 OIDC 的坑全在
"对方到底返回什么"上——实测就撞到 Dex 默认不发 `preferred_username`，
只有 `email` / `name`，而这正是接入时最容易卡住的一步。

⚠️ 起本地 IdP 时，issuer 必须是**浏览器和后端 Pod 都能解析到同一个地方**的地址。
用 `localhost` 的话浏览器指向自己、Pod 指向 Pod 自己；用 `host.docker.internal`
浏览器又解析不了。用宿主机的局域网 IP 是唯一两边都对的选择。

⚠️ 给采集用的集群凭据要用**真正的只读角色**。k8s 自带的 `view` 不含集群级资源
（nodes/PV），拿它去采会得到一句 `nodes is forbidden` —— 而这时候很容易图省事
绑 `cluster-admin`。自己定义一个只有 get/list/watch 的 ClusterRole 就够了。

### 5.6 反向代理一律 `proxy_set_header Host $http_host`

**`$host` 不含端口。** 每多一层代理写错，端口就再被吃掉一次，
而后端完全无从察觉——它只是以为自己跑在 `http://localhost` 上。

第一个撞上的是 OIDC：`redirect_uri` 拼成 `http://localhost/api/auth/sso/callback`
（少了 `:30833`），身份源回一句 `redirect_uri_mismatch`，
**既不说期望值也不说实际值**。接 SSO 卡住的人里有相当一部分卡在这。

实测一次踩了两层：产品自己的 chart 一处，本地 `k8s-proxy` 十七处。
只改一层不会有任何变化，很容易误判成"改的地方不对"。

适用范围不止 OIDC——**任何"后端需要知道自己对外是什么地址"的功能**
都栽在这一行上：回调地址、下载直链、邮件里的链接、Webhook 注册地址。
顺手把 `X-Forwarded-Host` / `X-Forwarded-Proto` 一起带上。

#### 5.6.1 `X-Forwarded-Proto` 不能写死 `$scheme`

多层代理时，**中间那层自己永远是明文 http**（TLS 在最外面终止），
所以这样写会把外面的 https 抹成 http：

```nginx
proxy_set_header X-Forwarded-Proto $scheme;   # ✗ 覆盖掉上游传来的真值
```

正确写法是「上游给了就用上游的，没给才用自己的」：

```nginx
map $http_x_forwarded_proto $fwd_proto {
    ""      $scheme;
    default $http_x_forwarded_proto;
}
proxy_set_header X-Forwarded-Proto $fwd_proto;
```

**为什么这条比看起来重要**：后端靠这个头决定会话 Cookie 要不要带 `Secure`。
写死 `$scheme` 的表现是——**浏览器走的是 https，Cookie 上却没有 `Secure`**。
功能全部正常，登录、跳转、接口一个不少，只有那道防线是空的，
而它在任何界面上都看不出来。

实测撞到过：给本地 SSO 加 https 入口后，最外层 nginx 明明传了 `X-Forwarded-Proto: https`，
Cookie 上的 `Secure` 就是不出现——被 Pod 里那层 nginx 的 `$scheme` 覆盖掉了。

⚠️ 验证要**两个方向都做**：走 https 进来的请求 Cookie 必须有 `Secure`，
容器内直接打明文的必须没有。只验一个方向的话，一个恒为 true 的实现也能过。

---

### 5.6.1 对外 URL 必须采信 `X-Forwarded-Proto`，不能用请求的 scheme

实测 ops-cmdb 单点登录页（站点是 `https://`）：

```
回调地址输入框：http://ops-cmdb-w.sl-devops.com/api/auth/sso/callback
                ^^^^
下方说明    ：把这一行**原样**登记到身份源的应用里，差一个字符，
              登录时对方只会回一句 redirect_uri_mismatch，
              既不说明期望值也不说明实际值。
```

**照着做必然配错**，而且撞上的正是这段说明自己警告的、最难排查的那个错误。

根因与 §5.6 同源：TLS 在入口网关终止，到后端已是明文 HTTP，
后端拿请求本身的 scheme 拼 URL 就得到 `http`。

**规则**：任何**给出去**的绝对 URL（OIDC redirect_uri、Webhook 回调、
邮件里的链接、分享链接）——

```
scheme = X-Forwarded-Proto ?? 配置的 external_base_url ?? 请求 scheme
```

最稳的是**给一个可配的 external base URL**，不依赖请求头。
入口链路有几层就要逐层确认转发了这个头（本项目实测踩到过两层）。

### 5.7 缺少配置时，宁可少一个功能，不要多一个后门

2026-08-20 在 ops-cmdb 的 `EnsureAdmin()` 里看到的写法，三条都值得全站沿用。

#### ① 「安全的失败方式」：不给配置就不建，而不是退回默认值

```go
pw := os.Getenv("ADMIN_PASSWORD")
if pw == "" {
    logx.Line("auth", "WARN 未设置 ADMIN_PASSWORD，**跳过创建本地 admin 账号**。"+
        "本地兜底登录通道因此不可用（SSO / 运维平台通道不受影响）。"+
        "需要它就设置 ADMIN_PASSWORD 后重启；绝不要使用默认口令。")
    return
}
```

原注释里的判断值得原样引用：

> ⚠️ 不建账号是**安全的失败方式**：SSO / 运维平台通道照常可用，只是少了本地兜底入口；
> 而"有一个人人都知道口令的全权账号"不是可以接受的失败方式。

**规则**：缺少安全相关配置时，正确的降级是**关掉那个功能**，不是**用一个内置默认值顶上**。
后者的危险在于它是**静默**的 —— 部署时没人会注意到自己漏设了变量。

#### ② 预先堵住「看似合理的错误修法」

```go
// ⚠️ 也不要改成随机口令后打进日志 —— 日志会被采集、会被转发。
```

**在注释里点名一个大概率会被想到、但同样错误的方案。**
否则下一个人会"顺手改进"成那个方案，而它并不更安全。

#### ③ 明确声明自己**没**做到什么

```go
// 口令强度下限。⚠️ 挡的是"随手填个 123"，不是完整的密码策略 ——
//	一个全放行账号配一个弱口令，和没设密码差别不大。
if len(pw) < 12 { ... }
```

**不夸大一个措施的作用范围。** 读代码的人因此知道：
还需要另外的密码策略，这一行不能替代它。

#### ⚠️ 但要配套检查：修复往往只覆盖「新建」，不覆盖「存量」

同一个函数里：

```go
if n > 0 {
    return          // ← 已存在的账号直接返回，不校验、不提示
}
```

**默认口令从代码里删掉了，但用旧逻辑建出来的账号原样还在。**
（实测生产 admin 仍是 `Unrestricted` 全权限、有活跃会话 ——
见 `docs/ops-issues/clusters/platform-ops-cmdb/OPSCMDB-074-*`。）

> **规则**：涉及安全默认值的修复，必须同时回答
> 「**已经按旧逻辑生成的那些怎么办**」。
> 至少要有一次**检测 + 告警**（不要自动改，那会把人锁在外面）。
